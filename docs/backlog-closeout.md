## Terms

- **`RUN59_BASE`**: `aaf24fa4df70b289cafc172f582569eccebff3a6`, the head of `main` when this spec was written (run 58 merged).
- **A render**: `renderFavorites()`, which ends in `renderDesktop()`; it recreates every tile node.
- **A started drag**: `dragSession !== null && dragSession.started === true` (the pointer moved 6 px or more). A press below that threshold is a tap, not a drag.
- **The drag grid**: the grid while a drag runs: `--rows` is `dragSession.rows` and `data-dragging="true"` (`applyDragVisuals`); it is as high as the allowed drop area, so it is taller than the grid at rest when the dragged tile is not alone in the lowest row.
- **Keyboard focus**: the focused tile matches `:focus-visible`.
- **The tooltip layer**: `#tooltip` (`showTooltipFor`, `hideTooltip`, `tooltipTrigger`).
- **An attempt**: the single in-flight weather request path of `retryWeather` (manual or automatic); **the load at open** is `startWeather`. Both own `weatherLoadInFlight`; an attempt raises `weatherGeneration` when it starts, the load at open does not (it keeps the value it started with).
- **The ensure chip**: `#desktop-status` showing `ENSURE_FAILED_MESSAGE`, set persistent at load when `ensureWidgetsLayout` threw (`widgetsEnsureFailed`). **A persistent chip** is any status that `desktopStatusPersistent` marks: the ensure chip, or the failed-heal chip with the `Reload` button (`showLayoutRestoreFailure`).
- **The opening click of a swap**: the pointer `click` (`detail > 0`) that moved the Add menu from the first level to the second (`Add weather tile…`). **The second press of a swap**: a `pointerdown` at most 300 ms after, and at most 4 px from, the opening click (compared by `event.timeStamp`, `clientX`, `clientY`), while the menu is open; it may land on the menu or outside it.
- **The post-close guard**: `armPostCloseClickGuard()`, `POST_CLOSE_CLICK_GUARD_MS` (300 ms): a pointer `click` (`detail > 0`) is swallowed and the default of a `mousedown` is cancelled while it runs; `backgroundPressed` respects it (`postCloseGuardActive()`).

## Rulings

Each Ruling is the author's decision with the alternative not taken and the price of being wrong. They go to Kier in the final report of the run (not into the backlog).

1. **Ruling (134): the render keeps the drag height.** Taken: while a drag has started, `renderDesktop` gives the new grid the drag grid's height (`max(its own rows, dragSession.rows)`) before it replaces the old one (decision 1). Not taken: running the page-height hold (`dragHoldPx`) during a drag, which needs a second set of rules for a state that has no settling. Price of a mistake: a drop after such a render lands one row off for a tile whose outline was valid; the outline and the write still agree (the outline is redrawn by `reattachDrag`).
2. **Ruling (154 (1)): one replay, by generation, remembered in `onBrowserOnline`.** Taken: `onBrowserOnline` remembers one `online` while `weatherLoadInFlight` is set (the load at open and every attempt), replays it once after that load or attempt ended as the current one, and forgets it when another attempt superseded the first (decision 2). The memory is taken before `retryWeather` is called, because `retryWeather` leaves at two different lines (the load at open at `!due`, an attempt at the in-flight line, stage 1 measurement) and one place beats two. Not taken: replay after success too (nothing to do, `weatherRefreshDue` is false), a retry loop, or leaving the load at open out of the rule (it is one more call of the same pure function, no more code). Price: one extra request to Open-Meteo for the stored city after a failed load or attempt, only while a weather tile is shown and the tab is visible.
3. **Ruling (154 (2) and (4)): the ensure retry is silent only when this tab never showed Settings.** Taken: a heal that succeeds is silent, and hides any persistent chip, only while `widgetsEnsureFailed` is true AND the state the tab showed before the heal had no Settings tile (decision 3); at the three heal sites the rule is the same pure function. Not taken: the flag alone at every site (the flag lives as long as the tab, so a real clear by another tab while Settings is shown would become silent: stage 1 I-2), and the return path only. Price: a person whose storage another tab really cleared while this tab showed no Settings does not see the reset notice (there was no layout of theirs to reset); on a mutation site the message stays unless the desk was partial (Accepted exception 10).
4. **Ruling (157): align the jiggle to the document timeline.** Taken: after each render in edit mode the new tile animations get `startTime = 0` (decision 5); the odd/even `animation-delay` stays what CSS says. Not taken: a CSS custom property holding the phase (it is up to one frame off), or leaving the jump (it is a polish row). Price: the animation start is overridden by script; if the browser refuses the assignment the tiles keep their own phase (the old behaviour).
5. **Ruling (159): the tooltip comes back for keyboard focus only, not after a resize.** Taken (decision 6). Not taken: also restoring a hover tooltip (hover returns by itself on the next pointer move, `AS-TRR-08`) and remembering the id in the resize handler (new code on a second path, for a window resize while a tile is in keyboard focus). Price: a hover tooltip that a render closed stays closed until the pointer moves; a tooltip that a resize closed stays closed until focus moves away and back.
6. **Ruling (148, keyboard scroll): hide, not follow.** Taken: any document scroll outside the focus window hides the tooltip (decision 7); the focus window is the clock (250 ms) or a one-shot flag, whichever still covers the event. Not taken: repositioning the tooltip on scroll (new behaviour, a per-frame layout read), or the clock alone (a starved frame delivers the scroll of a focus after 250 ms). Price: a keyboard user who scrolls with the arrow keys loses the tooltip and gets it back by moving focus away and onto the tile again; a real scroll in the one frame after a focus is ignored.
7. **Ruling (148, S3-01): shrink the footer buttons, no Accepted exception.** Taken: `min-width: 0` on the 50/50 footer buttons (decision 8). Not taken: keeping the 2.67 and 3.38 px as an Accepted exception. Price: at a font above 24 px the label and icon overflow the button's padding (they are inside the border at 24 px, outside it from about 26 px, which Kier put outside the project).
8. **Ruling (148, L2-02): a smaller option padding keyed to the browser's font size.** Taken: `padding` 4 px (from 5 px) in a media query on `rem` (decision 9). Not taken: a container query on the group (more CSS for a row of numbers), or an Accepted exception. Price: at an enlarged font in a window of 336 px or less the three-option groups lose 1 px of side padding each, invisible at the default font.
9. **Ruling (170 (2)): the alert is spoken once, with no flag.** Taken: `role` and `aria-live` come off the screen's paragraph when the Reset grid dialog first opens (decision 10); no module flag, because nothing rebuilds the screen after load (stage 1: `resize` returns at no state, the return re-read returns on an invalid meta, a confirmed reset reloads). Not taken: keeping the alert (the repeated announcement stays), a polite region, or a flag that no path can reach. Price: a screen reader user who comes back to this page after switching tabs does not hear the message again; the text stays in the page and the Reset grid button stays the one tab stop; a future path that rebuilt the screen would start with the alert again (one more announcement).
10. **Ruling (182): cancel the focus move of a press, not the click.** Taken: a `mousedown` on the backdrop or on a non-control part of a dialog in the first 300 ms of its life has its default cancelled (decision 11). Not taken: arming the post-close guard at open (run 57 refused it: it would swallow a deliberate click inside the new dialog). Price: none visible; the clicks that the backdrop already ignored stay ignored.
11. **Ruling (183): double press by time and distance, 300 ms and 4 px.** Taken: 300 ms and 4 px as the definition of the second press of a swap (decision 12), the length of the project's other guards. Not taken: 500 ms (the first draft: it swallows the first press of `dg-93` AS-WTA-05 (ii), which comes 459.9 and 461.7 ms after the swap click and 0.86 and 0.98 px from it, cited from the stage 1 skeptic, so `dg-93` would turn red or flaky), a 300 ms window over all presses (swallows the deliberate quick pick of the first second-level item, `AS-WTA-06`), a taller second-level box (draws an empty box for one hidden metric). Price: Kier's variant A cost, plus a third press in the same place is also lost; a double click slower than 300 ms behaves as today (the guard of a human double click is mostly under 300 ms; the operating system's 500 ms interval is not the rule here).
12. **Ruling (184): `aria-invalid` only for an error about the typed value.** Taken: invalid for the empty field and for a city that was not found, `aria-describedby` for every shown error (decision 13). Not taken: invalid for every error (a network failure says nothing about the value). Price: a screen reader says "invalid entry" for a not-found city and not for a network failure.
13. **Ruling (module boundaries): the new rules with logic are pure functions with unit tests.** Taken: the `online` memory and its replay decision, the second press of a swap, the silent-heal predicate and the city field's error attributes are pure functions in `weatherUiState.js` / `desktopUiState.js` (and `hasEverySystemTile` in `widgetsStore.js`), after the model of `weatherAppearanceDecision` and `deskRefreshDecision`; `newtab.js` only calls them (stage 1 M-8). Not taken: the same conditions inline in `newtab.js`, proven by source pins and E2E only. Price: four small exports and their tests.

## Decisions

1. **A render during a drag keeps the drag height (134).** While a drag has started (`dragSession?.started`), edit mode is on and the dragged tile is in the new layout (the same conditions under which `reattachDrag` goes on; otherwise it cancels and the render is exactly today's), `renderDesktop` sets `--rows` of the new grid to `max(its own rows, dragSession.rows)` and `data-dragging="true"` before it replaces the old grid, so the document is as high after the render as before it and the layout that `restoreFocus` forces has nothing to clamp. `reattachDrag` still picks up the dragged tile and redraws it and the outline, as today. Nothing else changes: with no started drag (a tap, no drag, a drag that ended, a cancelled one) the render is exactly today's, and the rule itself neither reads nor writes `dragHoldPx` or `dragSettling` (the existing `holding` branch still runs when a hold from an earlier drag is alive: it only ever shrinks the hold and is not touched). The effect: `scrollY` does not change and no tile moves under the pointer because of such a render.
2. **An `online` that arrives while a load or an attempt runs is remembered once (154 (1)).** `onBrowserOnline`, with the tab visible and a weather tile shown, asks a pure rule (`rememberOnline`, Ruling 13): when `weatherLoadInFlight` is set (the shared flag of the load at open and of every attempt, manual or automatic) the memory becomes the current `weatherGeneration` (one value, overwritten by a later `online`); then it calls `retryWeather` as today. The memory is taken there, before any exit of `retryWeather`, because the load at open leaves `retryWeather` at `!due` and an attempt at the in-flight line (P5): one place covers both and `retryWeather` is not changed for it. When the load at open (`startWeather`) or an attempt (`retryWeather`) ends as the current generation, after its result is applied and rendered, a second pure rule (`onlineReplayDecision(remembered, generation)`) says "replay" when the remembered value equals that generation, and the memory is cleared whatever it says (a value of another generation is dropped; a replay that the guards refuse leaves nothing behind, so a later return follows the ordinary tab-return rule). A replay first checks what its two callers check (`document.visibilityState === "visible"`, as `onBrowserOnline`; `navigator.onLine !== false`, as `onTabVisibilityChange`) and then calls `retryWeather({ automatic: true, ignorePause: true })`, whose own guards decide the rest (a shown tile, `weatherRefreshDue`), so after a success, or after a load that served a fresh cache, nothing starts. The early returns of a superseded load or attempt (a city change, a heal, a newer attempt raised the generation) clear nothing and replay nothing: the stale value can never equal a later generation. The memory is consumed on use: a failing replay never starts another; only a new `online` event can. A manual press does not supersede a running attempt (`startWeatherRetry` refuses it while one is in flight); it can supersede only a load at open whose tiles already show an error (a failed read of the city). What supersedes an attempt is a city change (`changeCity`) or the heal that drops a city (`dropCityClearedElsewhere`). The tab-return path (`onTabVisibilityChange`) is unchanged and remembers nothing.
3. **A heal that is this tab's own retry of a failed ensure is silent; a healthy re-read clears the ensure chip (154 (2) and (4)).** The question at a heal site is one pure rule (`healNotice`, Ruling 13): the heal is "silent" when `widgetsEnsureFailed` is true AND the state this tab showed before the heal (`widgetsState`, read before the heal's result replaces it) has no `chrome:settings` item; otherwise it is "reset" (today's message). On a heal that succeeds (`healClearedDesk` returns `healed`):
   - "silent": no `LAYOUT_RESET_MESSAGE`; `widgetsEnsureFailed` becomes false; and if `desktopStatusPersistent` is set (the ensure chip, or the `Reload` chip of an earlier failed heal) the chip is hidden (`showDesktopStatus("")`, which also drops `layoutFailureChipShown`). The sequence ensure failed, a return whose heal failed (the `Reload` chip), the fault gone, a second return, ends with no chip and no message.
   - "reset": as today (the message replaces any chip); the flag is not touched.
   - A failed heal is unchanged at every site (`LAYOUT_RESTORE_FAILED_MESSAGE`, the `Reload` chip) and the flag stays true.
   The rule is the same at the three heal sites (`healReadDesk` on a return, `runDesktopMutation`, `recoverFromGoneLink`). On a mutation site the shown state had Settings (edit mode needs the Settings tile, and Add link needs the Add tile), so the message stays there, except on a partial desk that shows Add but no Settings (Accepted exception 10). The fourth place that can write the reset message, `showWizardHealOutcome`, needs an enabled metric (`cityPrompt.js`), so it is unreachable with a failed ensure and is left as it is. On a return, a re-read state that has all six system tiles (the four `weather:` metrics, `chrome:settings`, `chrome:add`: the ids of `ENSURED_IDS`, exported from `widgetsStore.js` or mirrored by the pure `hasEverySystemTile(items)` there) clears the flag and the ensure chip (the persistent one with that text) even when it equals the shown state (the clear happens before the equal check, so an equal `#favorites` is not touched); a re-read state that has Settings but lacks another system tile leaves the chip and the flag, the claim "couldn't add the tiles" still being true. A mutation or a re-read whose fresh state is healthy and needs no heal leaves the flag and the chip as they are (the chip goes at the next action like any status; a flag that stays true is harmless, because the rule needs a shown state without Settings). No new text.
4. **The Edit weather city row follows an attempt (154 (3)).** After an attempt, manual or automatic, assigns a new `weatherLocation` (the replaced branch) or clears it (the `gone` branch) while an Edit weather dialog is open, `syncWeatherDialogCity()` runs. It returns at once, writing nothing, when the label it would write equals the one shown (the value, the hint and `aria-labelledby` unchanged), so a screen reader is not told the row again for no change. Focus, the typed fields and the rest of the dialog are untouched. With no change of the city the dialog is not touched at all (an equal label).
5. **The jiggle keeps its phase across renders (157).** In edit mode, at the end of `renderDesktop` (after the grid is attached, before any await), the animations named `tile-jiggle` of the new grid's tiles (`tile.getAnimations()`, `animationName === "tile-jiggle"`) get `startTime = 0` (the document timeline origin). The animation delay stays what CSS gave the tile (`animation-delay` is a property of the effect, not of the start), so every tile's active phase is `(timeline.currentTime - delay) mod 280 ms` with its own delay: a function of the clock only, whatever tile has which delay (`:nth-child(2n)` counts every child of the grid, badges and the drop outline included, so which tiles get -0.14 s is not a rule to rely on; measured, P2: the chrome tiles -0.14 s, the rest 0). A render therefore does not restart the jiggle and a tile created by a render joins the same phase. Only `tile-jiggle` is touched (the `tile-added` ring keeps its own start). With `prefers-reduced-motion: reduce` there are no animations and nothing is called. Mechanics are the implementer's choice inside this rule; the acceptance is AS-BC-03.
6. **The tooltip comes back for keyboard focus after a render (159).** `renderDesktop` remembers, before its first `hideTooltip()`, the widget id of `tooltipTrigger` when the tooltip is shown for a tile that is the focused element and matches `:focus-visible`. At the very end of `renderDesktop`, after `restoreFocus` and after the `scrollTo` of the `holding` branch (the tile's rectangle is read after the page is put back), if the focused element is that tile's new node (same `data-widget-id`, still `:focus-visible`) and the layers allow a tooltip (normal mode, no drag), `showTooltipFor` runs for it and the focus window of decision 7 opens (the render may scroll). The text is the new node's. A tooltip that was open for the pointer is not restored (the pointer opens it again on the next move); a tile that lost focus, a dialog that took it, edit mode and a drag restore nothing. This holds for every render that starts with such a tooltip open: the weather load at open, a manual or automatic attempt, a re-read on return, a city change. It does not hold for a window resize: the `resize` listener hides the tooltip at once and the render that follows runs a frame later, with nothing to remember (stage 1 SK-01; Accepted exception 3). The re-creation of the focused node itself is not touched.
7. **A document scroll hides the tooltip (148, keyboard scroll).** `onWindowScroll` (the passive `window` listener) first does what the `#favorites` capture listener does: unless the focus window covers it, `hideTooltip()`. The focus window is either the clock (`performance.now() < ignoreScrollUntil`, 250 ms after a focus or after decision 6's show) or a one-shot flag set by the `focusin` handler and by decision 6 and cleared by the next animation-frame callback after it (in the frame's rendering steps the scroll event of the scroll that the focus caused comes before the callbacks of the same frame, so a starved frame cannot deliver it after the 250 ms and hide the new tooltip; the clock stays for a smooth scroll that lasts longer). The existing `wheel` and `touchmove` listeners and the `#favorites` scroll listener stay. A hidden tooltip is shown again by the existing triggers (a pointer over, a new keyboard focus).
8. **The 50/50 footer buttons may shrink (148, S3-01).** `min-width: 0` on `.favorite-form__footer .button` (`src/controls.css`) and `.city-modal__actions .button` (`src/surfaces.css`; the footers of wizard steps 1 and 2 are this selector too, there is no third one), so two buttons of `flex: 1` are equal halves at every font size and never wider than their half. At 16 px and 20 px nothing changes (the content fits, the halves are what they were). The acceptance is in AS-BC-14; the mechanism is the one-line recommendation, confirmed by the stage 1 prototype (P8).
9. **A narrower option padding when the font is enlarged and the window is narrow (148, L2-02).** In `src/surfaces.css`, in a media query `(max-width: 14rem)` (the browser's default font size, as the query at the row stacking; at the default 16 px it is 224 px and never matches, at 24 px it is 336 px, and the bound is included: the rule is on at 336 px and off from 337 px), `.desktop-dialog .segmented__option` gets `padding: 0 4px` (from `0 5px`). Arithmetic from the cited numbers: the last label's slack is `23.6 - 5p` at the 17 px bar, so `p` of 4 gives 3.6 px (the stage 1 prototype measured 3.56); take the smallest reduction that meets AS-BC-15 (3 px if 4 px is not enough, for the radio groups only). The same rule covers every `.segmented` group of the dialogs (Icon, Color, Size, City label); the On tile toggles have their own focus ring (2 px, 2 to 4 px inside the option, `surfaces.css`, the block "A toggle group"), so a 3 px fallback never applies to them: if a toggle fails AS-BC-15 at 4 px it is a finding, not a reason to go lower. Nothing changes at 16 px and 20 px.
10. **The screen's alert is spoken once (170 (2)).** When the Reset grid dialog (`confirm-reset-grid`) first opens, `role` and `aria-live` come off the `p` of `.grid-unreadable` (the text stays). No module flag: nothing rebuilds the screen after load (Ruling 9). At first load the paragraph is still `role="alert"`, so the message is announced once as before. The Reset grid button, the dialog, the failure chip (`#desktop-status`, its own alert) and the `newer` screen's alert are unchanged.
11. **A press right after a dialog opened does not move the focus (182).** `openDesktopDialog` adds a `mousedown` listener on the backdrop and on the dialog root: within `DIALOG_BACKDROP_GUARD_MS` (300 ms) of the open, when the target is the backdrop or lies in the dialog but not inside an `input`, `button`, `label`, `select`, `textarea` or `a`, `preventDefault()` is called (the focus stays where `openDesktopDialog` put it). The backdrop's `click` guard, the Reset grid guard and every click handler are unchanged; no flag, timer or constant is added (`desktopDialogOpenedAt` and `DIALOG_BACKDROP_GUARD_MS` exist). After 300 ms a press on the backdrop moves the focus as today. This supersedes in part the note of `docs/wizard-trap-add-dblclick.md` that the focus after a double click on `Add link` (`body`) is not asserted (AS-WTA-07 and its Accepted exception 3).
12. **The second press of a swap does nothing (183, Kier's variant A).** The click that moves the Add menu to its second level (`add-weather` in `onAddMenuClick`) records its point and `event.timeStamp` when `event.detail > 0` (a pointer; a keyboard activation records nothing). In the document `pointerdown` listener of the Add menu, after the `!addMenuRoot` return and before its other conditions (the `contains` return and the outside press), a pure rule (`isSwapSecondPress(record, press)`, Ruling 13) decides: a press that falls within 300 ms and 4 px of the recorded click (compared by `event.timeStamp`, `clientX`, `clientY`) while the menu is open (`addMenuRoot`) calls `armPostCloseClickGuard()` and returns: the menu is not closed, nothing is restored, `addMenuDismissPress` is not set, and the guard swallows the `click` of that press, cancels its `mousedown` default and keeps `backgroundPressed` from leaving edit mode (the three Run 57 mechanisms, no new listener). The press may land on the menu or outside it. The record is dropped when the menu closes and is never older than 300 ms when read. Constants: `ADD_MENU_DOUBLE_PRESS_MS = 300` (the length of the project's other guards, `POST_CLOSE_CLICK_GUARD_MS`, `DIALOG_BACKDROP_GUARD_MS`; a human double click is mostly under 300 ms) and `ADD_MENU_DOUBLE_PRESS_SLOP_PX = 4` (a hand's tremor). Why not 500 ms: the `dg-93` recipe presses the second item of the three-item second level 459.9 and 461.7 ms after the swap click, 0.86 and 0.98 px from it (P10, cited), which 500 ms would swallow; 300 ms leaves it 160 ms outside, so `dg-93` stays green with no change. A press elsewhere, after 300 ms, or 40 px away (the first item of the second level, the quick pick of `AS-WTA-06`: the swap click and the pick are 40 px apart) behaves as today. With three hidden metrics the second press lands on the second level's item and its click is swallowed (nothing restored, the second level stays open); with one hidden metric it lands outside the shorter menu and does not close it; with a link tile under the point its click does not open `edit-link`.
13. **The city field names its error (184).** The error slot `p[data-city-modal-error]` gets a stable `id` (one city form exists at a time). While the slot shows a message the input has `aria-describedby` equal to that id; when the slot is empty or hidden the attribute is removed. `aria-invalid="true"` is set only while the message is about the typed value: `Enter a city name` (the empty submit by Enter, in the city modal and on wizard step 1; the buttons are disabled for an empty field) and a city that was not found (`City "…" was not found`: the catch of `changeCity` with `error.kind === "notFound"`). Every other message (network, timeout, rate limit, unknown, and a location lookup failure, which has its own `notFound` reason in `cityLocation.js` and is written by a different path) is described but the field is not invalid. The kind cannot be read from the message text or from `kind` alone, so the seven writers of a non-empty `cityModalError` (the three empty submits, the catch of `changeCity`, the three location failures) set a second module value, `cityModalErrorInvalid`, next to it; the pure `cityFieldErrorAttributes(message, invalid)` returns `{ describedBy, invalid }`; one helper applies it, and the three DOM writers (the form build, `syncCityModal`, `clearCityError`) call that helper. Both attributes are cleared by `clearCityError` (typing) and by every path that empties or hides the slot, and are absent on a new form. No new text: the existing messages are the descriptions. The model is `showDialogError` of the link dialog (`docs/link-dialog-validation.md` decision 3).
14. **Backlog 133 is three wording fixes, no behaviour.** In `docs/drag-scroll-target.md`: (a) decision 2b (iii): "the content does not move" holds as far as the old hold covers; beyond it the browser clamps `scrollY` exactly as on `main` (the rule is `h_new = min(formula, h_old)`, and the Non-goals already say so); (b) AS-DST-05 (e) states its two directions: (e1) the window shrinks by 40 px, `scrollY` and the tiles stay within 1 px and the hold is recomputed down; (e2) the window grows by 40 px, the only scroll change is the browser's own clamp to the taller window and `scrollHeight` is not higher than the held one (this is what `dg-87` already measures for `delta` -40 and 40); (c) the Intake log row of run 13 says "no `window` or `document` `scroll` listener during a drag" instead of "no `scroll` listener" (the capture listener on `#favorites` is the tooltip's and does not see document scrolls). After decision 1 of this spec the Non-goal "weather renders during a drag" of `docs/drag-scroll-target.md` is superseded in part (a note, not an edit of its text elsewhere).

### AS-BC-01 A render during a drag keeps the page where it is (134)
- Given: a desk taller than the window (the 188-link desk of `dg-87`), edit mode, a drag started (tile held, pointer over the grid) and the page autoscrolled to the bottom of the drag grid; premise printed: `scrollY` above the resting maximum (`scrollHeight` of the resting grid minus `clientHeight`) and `document.activeElement` (the pressed tile, which a pointer press focuses; the forced layout of its re-focus is what clamps the page, P1). Stale weather tiles. Windows: 1280×800, 500×800 and 320×600.
- When: a render happens mid-drag with the pointer still held and still: an `online` event (an automatic attempt that fails, then the same attempt succeeding in a second run); a manual retry is not possible during a drag.
- Then: `scrollY` is the same value before the render, after it, and one second later (±1); every tile rectangle other than the dragged one is unchanged (±1); the held tile is still under the pointer (±1); the document height is unchanged (±1); the outline is on the cell it was judged for. A control: the same render with the focus on `body` (the pressed tile blurred before the render) changes nothing either.
- Red on `RUN59_BASE` (premise): `scrollY` drops by a row at the render.
- Verified by: E2E `dg-95` group 1; `newtabSource` pin (the new grid gets the drag rows, `max(own, dragSession.rows)`, before `replaceChildren`, only while `dragSession.started`).

### AS-BC-02 The drop after such a render lands on the outline
- Given: AS-BC-01 after the render.
- When: the pointer moves to a free cell and is released.
- Then: the tile is written to the outlined cell (one write, `moveWidget`); `scrollY` is unchanged by the release (±1; the hold of `docs/drag-scroll-target.md` as before); and the same drag with no render in the middle gives the same cell. A render in the middle of a drag that never started (a tap) changes nothing, and neither does a render with no drag (a control: today's behaviour).
- Verified by: E2E `dg-95` group 1.

### AS-BC-03 The jiggle does not restart at a render (157)
- Given: edit mode, 1280×800 and 500×800, several tiles including a 2×1 and the chrome tiles; premise printed: every tile has a running `tile-jiggle` animation and its `delay`, read from `animation.effect.getComputedTiming().delay` (measured: -140 ms for the chrome tiles, 0 for the rest, because `:nth-child(2n)` counts the badges and the outline too; the scenario does not assume which tiles have which delay).
- When: at least three renders at different times in edit mode, separated by pauses that are not multiples of 280 ms (for example 97, 131 and 173 ms): a stale tile's automatic attempt (an `online` event) and the close of the Add link dialog are used (a manual retry press is normal mode, so not edit mode); then a link is added (a new tile appears in the same render path).
- Then: after every render, for every tile, `(animation.currentTime - delay) mod 280` is within 20 ms (circular distance) of `(document.timeline.currentTime - delay) mod 280`, read in the same task (the phase is a function of the clock, each tile with its own delay); each tile's `delay` is the same as before the render (the 140 ms stagger is kept); the tile created by the render is in phase with the others. With `prefers-reduced-motion: reduce` there are no `tile-jiggle` animations before or after, and the dashed outline is as before.
- Red on `RUN59_BASE` (premise, probabilistic): on the base the phase after a render is the time since the render, so one render lies beyond 20 ms of the clock phase with probability about 86%; the scenario requires that at least one of the three renders deviates on the base (the chance that all three pass on the base is under 1%). On the head all of them are within 20 ms.
- Verified by: E2E `dg-95` group 2; `newtabSource` pin.

### AS-BC-04 The tooltip comes back for a keyboard-focused tile after a render (159)
- Given: normal mode; a stale weather tile (a retry button) focused by Tab (not by script after a pointer press); premise printed: the tooltip is shown with the tile's description and `:focus-visible` is true. Also: the hint tile (no city) focused by Tab with the tooltip `Set a city`.
- When: a render happens (an automatic attempt on `online` that succeeds, then one that fails; a manual attempt by Enter on the retry button; the render of an Add menu restore is edit mode, so not used).
- Then: after the render the focused element is the tile with the same `data-widget-id` (a new node), `#tooltip` is shown within one frame with the new node's text (the new description after a success, the stale one after a failure), placed by the same rule and beside the tile in its position after the render (the page was put back first); the tooltip is not restored when (a) the tile was hovered but not keyboard-focused (hover case: the tooltip is closed by the render and the pointer opens it on the next move, `AS-TRR-08` unchanged), (b) focus is not on a tile (a dialog open: the attempt runs behind the inert grid, no tooltip), (c) edit mode is on, (d) a drag is on, (e) the render comes from a window resize that changes the column count (control: the `resize` listener hides the tooltip before the render, which restores nothing; the tooltip stays hidden until focus moves away and back).
- Red on `RUN59_BASE` (premise): the tooltip stays hidden after the render.
- Verified by: E2E `dg-95` group 3; `dg-90` AS-TRR-06 (h) is updated in the same task.

### AS-BC-05 A document scroll hides the tooltip; the scroll a focus causes does not (148, keyboard scroll)
- Given: a desk taller than the window, a weather tile in view, focused by Tab, tooltip shown; premise printed: the tooltip is shown and the document can scroll.
- When: (a) ArrowDown or PageDown with the tile still focused; (b) a wheel scroll over the page; (c) a drag of the scrollbar is not automated (a `scrollTo` through the harness stands for it); (d) Tab onto a tile that is below the window edge, so the browser scrolls it into view; (d2) as (d), and the main thread is busy for 300 ms (a synchronous loop in the page) right after the Tab, so the frame that carries the focus scroll comes after the 250 ms clock window.
- Then: (a), (b), (c) the tooltip is hidden after the scroll event (within one frame) and shows again after moving focus away and onto the tile; (d) and (d2) the tooltip of the newly focused tile is shown at the end (the clock window or the one-shot flag protects it from its own scroll) and is placed beside the tile in its scrolled position.

- Verified by: E2E `dg-95` group 3.

### AS-BC-06 An `online` during a load or an attempt is replayed once after it (154 (1))
- Given: a city set, weather tiles stale (cache older than 30 minutes) in 1280×800; the network holds the forecast request (`net.hold`).
- When: (a) an automatic attempt starts (a tab return), then at 1 s an `online` event, then the held request fails (`net.release({ abort: true })`); the same with a manual attempt (Enter on a stale tile's retry button) in place of the tab return; (b) the same as (a) with the held request succeeding; (c) the same as (a), but a city change (the Edit weather dialog, its city field, a new city, Save) completes while the attempt is held, so the generation is raised, then the held request is released; (d) the same as (a) with the tab hidden when the first attempt fails; (e) two `online` events during one attempt; (f) the replay itself fails; (g) a slow success: the `online` at 1 s, the first request held longer than 15 s (`CITY_REQUEST_TIMEOUT_MS`, `withTimeout`), so the attempt fails by timeout at 15 s and the replay starts; the first request is then released with a success (its late answer writes the cache and changes no tile: Accepted exception 17 of `docs/tab-return-refresh.md`), and the replay's own request is answered normally; (h) the load at open: a tab opened with a city and a cache older than 30 minutes, the first request held, an `online` at 1 s, the held request fails.
- Then: (a) after the first attempt ends, within 500 ms one more attempt starts (the requests counter grows by one attempt's worth; the pause of 3 s is ignored) and, if the network now answers, the tiles show the new values with no status text and no announcement; (b) no extra attempt (the cache is fresh, `weatherRefreshDue` is false); (c) no extra attempt for that `online` (the city change superseded the attempt); (d) no extra attempt while hidden (the memory is cleared at the attempt's end, so a later return follows the ordinary tab-return rule); (e) exactly one replay; (f) no third attempt (only a new `online` can start one); (g) never more than one attempt in flight, the tiles end `ready` with the fresh values of the replay, the requests counter is bounded (the first attempt's two requests plus the replay's two), no status text, no announcement; (h) after the load ends within 500 ms one attempt starts (the same bounds as (a)) and the tiles end `ready`; with the held request succeeding instead, no extra attempt; in all cases at most one attempt runs at a time and no request is made with no shown tile.
- Red on `RUN59_BASE` (premise): (a) and (h) no further request after the failure.
- Verified by: E2E `dg-95` group 4 (the held-request recipes of `dg-90` G6 and `lib/tabReturn.mjs`); unit tests of `rememberOnline` and `onlineReplayDecision`.

## Accepted exceptions

1. **A deliberate quick second press is lost (183).** Kier's price of variant A: a press within 300 ms and 4 px of the click that moved the menu to its second level does nothing, so does a third press there; and the 300 ms post-close guard that the swallowed press arms also swallows any deliberate pointer press in those 300 ms (the same trade as the other guarded closes, `docs/wizard-trap-add-dblclick.md` Accepted exception 1). A double click slower than 300 ms behaves as before (the window was 500 ms in revision 1; Ruling 11).
2. **A press does not move the focus in the first 300 ms of a dialog (182).** A press on the backdrop or on a non-control part of a dialog within 300 ms of its open leaves the focus where it was; clicks (the backdrop's own guard ignores them) and presses on controls are not touched.
3. **A hover tooltip is not restored, and a resize closes the tooltip for good (159).** After a render the tooltip of a keyboard-focused tile returns; one that was open for the pointer stays closed until the pointer moves (`AS-TRR-08`). A window resize hides the tooltip by its own listener, before the render runs; the render restores nothing, and the tooltip comes back only when focus moves away and onto the tile (stage 1 I-3, SK-01).
4. **A scroll hides the tooltip (148).** Keyboard, wheel and scrollbar scrolls hide it; it does not follow the tile.
5. **The alert is not repeated (170).** After the Reset grid dialog first opens, the screen's paragraph is plain text; a screen reader user who comes back to the page without a reload does not hear it again. A real screen reader was not run; the owner's VoiceOver smoke (roadmap, "Только Кир") is the check.
6. **The jiggle starts at an arbitrary phase when edit mode is entered (157).** It is a function of the clock, not of the moment of the click; invisible.
7. **A replay can come after a replay's own cause is gone (154 (1)).** The replay goes through the ordinary guards (`due`, a shown tile, a visible tab, online), so a state that changed meanwhile is respected; the only residue is one request for the stored city after a failure.
8. **Fonts above 24 px stay out (148).** The geometry fixes are measured to 24 px; 32 px and more is outside the project (Kier, 2026-11-15, rows 148 L3-01 and 170 (1)).
9. **The accessibility tree, not a speech output, is measured (170, 184).** `aria-invalid`, `aria-describedby`, `role` and the computed description are asserted; what VoiceOver says is not.
10. **A silent heal on a mutation site only for a partial desk (154 (2)).** The rule is the same at the three heal sites, but a mutation site has Settings in the shown state (edit mode and Add link need tiles that a failed ensure does not leave), so there the reset message stays; a partial desk that shows Add and no Settings heals silently there. That sub-case is proven by the unit test of the pure rule, not by an E2E scenario (it needs a seeded partial desk with an ensure that fails).
11. **The equal-state ensure chip clear may be unit-tested only (154 (4)).** The chip clears before the equal check; the E2E needs a fault that fails only the ensure on a full storage, which the harness lacks (AS-BC-08 (ii)). Without one the branch is covered by the unit test of `hasEverySystemTile` and a source pin of the order.
12. **A scroll in the one frame after a focus is ignored (148).** The one-shot flag of decision 7 does not tell a real scroll from the focus's own in that frame; the tooltip survives it. Invisible.
