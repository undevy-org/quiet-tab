## Terms

- **`RUN59_BASE`**: `aaf24fa4df70b289cafc172f582569eccebff3a6`, the head of `main` when this spec was written (run 58 merged).
- **A render**: `renderFavorites()`, which ends in `renderDesktop()`; it recreates every tile node.
- **A started drag**: `dragSession !== null && dragSession.started === true` (the pointer moved 6 px or more). A press below that threshold is a tap, not a drag.
- **The drag grid**: the grid while a drag runs: `--rows` is `dragSession.rows` and `data-dragging="true"` (`applyDragVisuals`); it is as high as the allowed drop area, so it is taller than the grid at rest when the dragged tile is not alone in the lowest row.
- **Keyboard focus**: the focused tile matches `:focus-visible`.
- **The tooltip layer**: `#tooltip` (`showTooltipFor`, `hideTooltip`, `tooltipTrigger`).
- **An attempt**: the single in-flight weather request path of `retryWeather` (manual or automatic); **the load at open** is `startWeather`. Both own `weatherLoadInFlight`; an attempt raises `weatherGeneration` when it starts, the load at open does not (it keeps the value it started with).
- **The ensure chip**: `#desktop-status` showing `ENSURE_FAILED_MESSAGE`, set persistent at load when `ensureWidgetsLayout` threw (`widgetsEnsureFailed`). **A persistent chip** is any status that `desktopStatusPersistent` marks: the ensure chip, or the failed-heal chip with the `Reload` button (`showLayoutRestoreFailure`).
- **The opening click of a swap**: the pointer `click` (`detail > 0`) that moved the Add menu from the first level to the second (`Add weather tile…`). **The second press of a swap**: a `pointerdown` at most 300 ms after, and at most 4 px from, the opening click (compared by `event.timeStamp`, `clientX`, `clientY`), while the menu is open; it may land on the menu or outside it.
- **The post-close guard**: `armPostCloseClickGuard()`, `POST_CLOSE_CLICK_GUARD_MS` (300 ms): a pointer `click` (`detail > 0`) is swallowed and the default of a `mousedown` is cancelled while it runs; `backgroundPressed` respects it (`postCloseGuardActive()`).

## Rulings

Each Ruling is the author's decision with the alternative not taken and the price of being wrong. They go to Kier in the final report of the run (not into the backlog).

1. **Ruling (134): the render keeps the drag height.** Taken: while a drag has started, `renderDesktop` gives the new grid the drag grid's height (`max(its own rows, dragSession.rows)`) before it replaces the old one (decision 1). Not taken: running the page-height hold (`dragHoldPx`) during a drag, which needs a second set of rules for a state that has no settling. Price of a mistake: a drop after such a render lands one row off for a tile whose outline was valid; the outline and the write still agree (the outline is redrawn by `reattachDrag`).
2. **Ruling (154 (1)): one replay, by generation, remembered in `onBrowserOnline`.** Taken: `onBrowserOnline` remembers one `online` while `weatherLoadInFlight` is set (the load at open and every attempt), replays it once after that load or attempt ended as the current one, and forgets it when another attempt superseded the first (decision 2). The memory is taken before `retryWeather` is called, because `retryWeather` leaves at two different lines (the load at open at `!due`, an attempt at the in-flight line, stage 1 measurement) and one place beats two. Not taken: replay after success too (nothing to do, `weatherRefreshDue` is false), a retry loop, or leaving the load at open out of the rule (it is one more call of the same pure function, no more code). Price: one extra request to Open-Meteo for the stored city after a failed load or attempt, only while a weather tile is shown and the tab is visible.
3. **Ruling (154 (2) and (4)): the ensure retry is silent only when this tab never showed Settings.** Taken: a heal that succeeds is silent, and hides any persistent chip, only while `widgetsEnsureFailed` is true AND the state the tab showed before the heal had no Settings tile (decision 3); at the three heal sites the rule is the same pure function. Not taken: the flag alone at every site (the flag lives as long as the tab, so a real clear by another tab while Settings is shown would become silent: stage 1 I-2), and the return path only. Price: a person whose storage another tab really cleared while this tab showed no Settings does not see the reset notice (there was no layout of theirs to reset); on a mutation site the message stays unless the desk was partial (Accepted exception 10).
4. **Ruling (157): align the jiggle to the document timeline.** Taken: after each render in edit mode the new tile animations get `startTime = 0` (decision 5); the odd/even `animation-delay` stays what CSS says. Not taken: a CSS custom property holding the phase (it is up to one frame off), or leaving the jump (it is a polish row). Price: the animation start is overridden by script; if the browser refuses the assignment the tiles keep their own phase (the old behaviour).
5. **Ruling (159): the tooltip comes back for keyboard focus only, not after a resize.** Taken (decision 6). Not taken: also restoring a hover tooltip (hover returns by itself on the next pointer move, `AS-TRR-08`) and remembering the id in the resize handler (new code on a second path, for a window resize while a tile is in keyboard focus). Price: a hover tooltip that a render closed stays closed until the pointer moves; a tooltip that a resize closed stays closed until focus moves away and back.
6. **Ruling (148, keyboard scroll): hide, not follow.** Taken: any document scroll outside the focus window hides the tooltip (decision 7); the focus window is the clock (250 ms by `performance.now()` after a focus, or after the render that brought the tooltip back) or a one-shot flag, whichever still covers the event. Not taken: repositioning the tooltip on scroll (new behaviour, a per-frame layout read), or the clock alone (a starved frame delivers the scroll of a focus after 250 ms). Price: a keyboard user who scrolls with the arrow keys loses the tooltip and gets it back by moving focus away and onto the tile again; and a real scroll that starts within 250 ms of a focus (or of the tooltip coming back after a render), for example PageDown pressed straight after Tab, does not hide the tooltip: it stays until the next scroll (Accepted exception 12). The window is a time, not "one frame".
7. **Ruling (148, S3-01): shrink the footer buttons, no Accepted exception.** Taken: `min-width: 0` on the 50/50 footer buttons (decision 8). Not taken: keeping the 2.67 and 3.38 px as an Accepted exception. Price: at a font above 24 px the label and icon overflow the button's padding (they are inside the border at 24 px, outside it from about 26 px, which Kier put outside the project).
8. **Ruling (148, L2-02): a smaller option padding keyed to the browser's font size.** Taken: `padding` 4 px (from 5 px) in a media query on `rem` (decision 9). Not taken: a container query on the group (more CSS for a row of numbers), or an Accepted exception. Price: at an enlarged font in a window of 336 px or less the three-option groups lose 1 px of side padding each, invisible at the default font.
9. **Ruling (170 (2)): the alert is spoken once, with no flag.** Taken: `role` and `aria-live` come off the screen's paragraph when the Reset grid dialog first opens (decision 10); no module flag, because nothing rebuilds the screen after load (stage 1: `resize` returns at no state, the return re-read returns on an invalid meta, a confirmed reset reloads). Not taken: keeping the alert (the repeated announcement stays), a polite region, or a flag that no path can reach. Price: a screen reader user who comes back to this page after switching tabs does not hear the message again; the text stays in the page and the Reset grid button stays the one tab stop; a future path that rebuilt the screen would start with the alert again (one more announcement).
10. **Ruling (182): cancel the focus move of a press, not the click.** Taken: a `mousedown` on the backdrop or on a non-control part of a dialog in the first 300 ms of its life has its default cancelled (decision 11). Not taken: arming the post-close guard at open (run 57 refused it: it would swallow a deliberate click inside the new dialog). Price: none visible; the clicks that the backdrop already ignored stay ignored.
11. **Ruling (183): double press by time and distance, 300 ms and 4 px.** Taken: 300 ms and 4 px as the definition of the second press of a swap (decision 12), the length of the project's other guards. Not taken: 500 ms (the first draft: it swallows the first press of `dg-93` AS-WTA-05 (ii), which comes 459.9 and 461.7 ms after the swap click and 0.86 and 0.98 px from it, cited from the stage 1 skeptic, so `dg-93` would turn red or flaky), a 300 ms window over all presses (swallows the deliberate quick pick of the first second-level item, `AS-WTA-06`, whose item is 40 px from the swap point when the menu stands below the Add tile), a taller second-level box (draws an empty box for one hidden metric). Price: Kier's variant A cost, plus a third press within 300 ms of the opening click in the same place is also lost (a third press later than that is an ordinary press, but not one that falls in the 300 ms guard that a swallowed second press armed: with the second at 120 ms that guard lasts to about 420 ms, so a third press on a menu item at 350 ms does nothing either; Accepted exception 1); a deliberate quick pick of an item that lies within 4 px of the swap point is lost too, which happens when the menu stands above the Add tile (Accepted exception 14); a double click slower than 300 ms behaves as today (the guard of a human double click is mostly under 300 ms; the operating system's 500 ms interval is not the rule here).
12. **Ruling (184): `aria-invalid` only for an error about the typed value.** Taken: invalid for the empty field and for a city that was not found, `aria-describedby` for every shown error (decision 13). Not taken: invalid for every error (a network failure says nothing about the value). Price: a screen reader says "invalid entry" for a not-found city and not for a network failure.
13. **Ruling (module boundaries): the new rules with logic are pure functions with unit tests.** Taken: the `online` memory and its replay decision, the second press of a swap, the silent-heal predicate and the city field's error attributes are pure functions in `weatherUiState.js` / `desktopUiState.js` (and `hasEverySystemTile` in `widgetsStore.js`), after the model of `weatherAppearanceDecision` and `deskRefreshDecision`; `newtab.js` only calls them (stage 1 M-8). Not taken: the same conditions inline in `newtab.js`, proven by source pins and E2E only. Price: six small exports (two pairs and two singles: `rememberOnline` with `onlineReplayDecision`, `healNotice` with `hasEverySystemTile`, `isSwapSecondPress`, `cityFieldErrorAttributes`) and their tests.

## Decisions

1. **A render during a drag keeps the drag height (134).** While a drag has started (`dragSession?.started`), edit mode is on and the dragged tile is in the new layout (the same conditions under which `reattachDrag` goes on; otherwise it cancels and the render is exactly today's), `renderDesktop` sets `--rows` of the new grid to `max(its own rows, dragSession.rows)` and `data-dragging="true"` before it replaces the old grid, so the document is as high after the render as before it and the layout that `restoreFocus` forces has nothing to clamp. `reattachDrag` still picks up the dragged tile and redraws it and the outline, as today. Nothing else changes: with no started drag (a tap, no drag, a drag that ended, a cancelled one) the render is exactly today's, and the rule itself neither reads nor writes `dragHoldPx` or `dragSettling` (the existing `holding` branch still runs when a hold from an earlier drag is alive: it only ever shrinks the hold and is not touched). The effect: `scrollY` does not change and no tile moves under the pointer because of such a render. When a hold from an earlier drag is alive, the hold branch's own measurement (the hold reset to 0, the document measured) can clamp `scrollY` before `reattachDrag` judges the target, and putting the page back in the same task sends no `scroll` event for `onWindowScroll` to judge it again; so after that `scrollTo` a started drag judges its target once more (`updateDragTarget`), and the outline stays on the cell under the pointer (stage 4 measurement, `## Live measurement` P1; AS-BC-01 (ii)).
2. **An `online` that arrives while a load or an attempt runs is remembered once (154 (1)).** `onBrowserOnline`, with the tab visible and a weather tile shown, asks a pure rule (`rememberOnline`, Ruling 13): when `weatherLoadInFlight` is set (the shared flag of the load at open and of every attempt, manual or automatic) the memory becomes the current `weatherGeneration` (one value, overwritten by a later `online`; "no memory" is `null`, and `0`, the generation of the load at open, is a valid value, so the rule compares with `null` and never tests truthiness); then it calls `retryWeather` as today. The memory is taken there, before any exit of `retryWeather`, because the load at open leaves `retryWeather` at `!due` and an attempt at the in-flight line (P5): one place covers both and `retryWeather` is not changed for it. When the load at open (`startWeather`) or an attempt (`retryWeather`) ends as the current generation, after its result is applied and rendered, a second pure rule (`onlineReplayDecision(remembered, generation)`) says "replay" when the remembered value equals that generation, and the memory is cleared whatever it says (a value of another generation is dropped; a replay that the guards refuse leaves nothing behind, so a later return follows the ordinary tab-return rule). The clear happens in every outcome of a load or attempt that is still current, the `gone` outcome included (that branch of `retryWeather` returns before the replay point today; it gets the one clearing line, so the rule is the same on every path; the value could not match a later generation anyway, the generations only grow). A replay first checks what its two callers check (`document.visibilityState === "visible"`, as `onBrowserOnline`; `navigator.onLine !== false`, as `onTabVisibilityChange`) and then calls `retryWeather({ automatic: true, ignorePause: true })`, whose own guards decide the rest (a shown tile, `weatherRefreshDue`), so after a success, or after a load that served a fresh cache, nothing starts. The early returns of a superseded load or attempt (a city change, a heal, a newer attempt raised the generation) clear nothing and replay nothing: the stale value can never equal a later generation. The memory is consumed on use: a failing replay never starts another; only a new `online` event can. A manual press does not supersede a running attempt (`startWeatherRetry` refuses it while one is in flight); it can supersede only a load at open whose tiles already show an error (a failed read of the city). What supersedes an attempt is a city change (`changeCity`) or the heal that drops a city (`dropCityClearedElsewhere`). The tab-return path (`onTabVisibilityChange`) is unchanged and remembers nothing.
3. **A heal that is this tab's own retry of a failed ensure is silent; a healthy re-read clears the ensure chip (154 (2) and (4)).** The question at a heal site is one pure rule (`healNotice`, Ruling 13): the heal is "silent" when `widgetsEnsureFailed` is true AND the state this tab showed before the heal (`widgetsState`, read before the heal's result replaces it) has no `chrome:settings` item; otherwise it is "reset" (today's message). On a heal that succeeds (`healClearedDesk` returns `healed`):
   - "silent": no `LAYOUT_RESET_MESSAGE`; `widgetsEnsureFailed` becomes false; and if `desktopStatusPersistent` is set (the ensure chip, or the `Reload` chip of an earlier failed heal) the chip is hidden (`showDesktopStatus("")`, which also drops `layoutFailureChipShown`). The sequence ensure failed, a return whose heal failed (the `Reload` chip), the fault gone, a second return, ends with no chip and no message. When the chip is hidden by a silent heal and the focus is inside it (on `Reload`: `desktopStatus.contains(document.activeElement)`, read BEFORE the chip is hidden, because hiding a focused element drops the focus to `body`), the focus goes to the `chrome:settings` tile with `preventScroll` (the healed grid has it; `dismissLayoutFailureChip` returns focus to the desk container for Escape, and a silent heal has a better target); one helper does the hide-and-refocus for the silent branch of the three sites. A silent heal whose chip does not hold the focus moves the focus nowhere new (the existing `healReadDesk` rule for a focused tile stays).
   - "reset": as today (the message replaces any chip); the flag is not touched.
   - A failed heal is unchanged at every site (`LAYOUT_RESTORE_FAILED_MESSAGE`, the `Reload` chip) and the flag stays true.
   What a "silent" heal shows at each site: `healReadDesk` nothing; `runDesktopMutation` nothing (it writes no status of its own on success); `recoverFromGoneLink` shows `error.message`, as it does today when nothing was healed (its message about the gone link is still true; only the reset notice is dropped). The rule is the same at the three heal sites (`healReadDesk` on a return, `runDesktopMutation`, `recoverFromGoneLink`). On a mutation site the shown state had Settings (edit mode needs the Settings tile, and Add link needs the Add tile), so the message stays there, except on a partial desk that shows Add but no Settings (Accepted exception 10). The fourth place that can write the reset message, `showWizardHealOutcome`, needs an enabled metric (`cityPrompt.js`), so it is unreachable with a failed ensure and is left as it is. On a return, a re-read state that has all six system tiles (the four `weather:` metrics, `chrome:settings`, `chrome:add`: the ids of `ENSURED_IDS`, exported from `widgetsStore.js` next to the constant (one source of truth) and used by the pure `hasEverySystemTile(items)` there; it counts the PRESENCE of an item with that id, as `ensureWidgetsLayout` does with `readable(id) === null`, so a metric hidden by the user (`enabled: false`) is present and does not keep the chip) clears the flag and the ensure chip (the persistent one with that text) even when it equals the shown state (the clear happens before the equal check, so an equal `#favorites` is not touched); a re-read state that has Settings but lacks another system tile leaves the chip and the flag, the claim "couldn't add the tiles" still being true. A mutation or a re-read whose fresh state is healthy and needs no heal leaves the flag and the chip as they are (the chip goes at the next action like any status; a flag that stays true is harmless, because the rule needs a shown state without Settings). The `Reload` chip of an earlier failed heal is not cleared by such a healthy re-read either (only a silent heal, above, hides it): a `Reload` chip standing over a grid that a healthy re-read already shows is the behaviour of `RUN59_BASE`, found on the way and left alone here (Non-goals; `pipeline/backlog.md` row 185). No new text.
4. **The Edit weather city row follows an attempt (154 (3)).** After an attempt, manual or automatic, assigns a new `weatherLocation` (the replaced branch) or clears it (the `gone` branch), or a load at open ends successfully and assigns it (`startWeather`), while an Edit weather dialog is open, `syncWeatherDialogCity()` runs. It returns at once, writing nothing, when the label it would write equals the one shown (the value, the hint and `aria-labelledby` unchanged), so a screen reader is not told the row again for no change. Focus, the typed fields and the rest of the dialog are untouched. With no change of the city the dialog is not touched at all (an equal label).
5. **The jiggle keeps its phase across renders (157).** In edit mode, at the end of `renderDesktop` (after the grid is attached, before any await), the animations named `tile-jiggle` of the new grid's tiles (`tile.getAnimations()`, `animationName === "tile-jiggle"`) get `startTime = 0` (the document timeline origin). The animation delay stays what CSS gave the tile (`animation-delay` is a property of the effect, not of the start), so every tile's active phase is `(timeline.currentTime - delay) mod 280 ms` with its own delay: a function of the clock only, whatever tile has which delay (`:nth-child(2n)` counts every child of the grid, badges and the drop outline included, so which tiles get -0.14 s is not a rule to rely on; measured, P2: the chrome tiles -0.14 s, the rest 0). A render therefore does not restart the jiggle and a tile created by a render joins the same phase. Only `tile-jiggle` is touched (the `tile-added` ring keeps its own start). With `prefers-reduced-motion: reduce` there are no animations and nothing is called. Mechanics are the implementer's choice inside this rule; the acceptance is AS-BC-03.
6. **The tooltip comes back for keyboard focus after a render (159).** `renderDesktop` remembers, before its first `hideTooltip()`, the widget id of `tooltipTrigger` when the tooltip is shown for a tile that is the focused element and matches `:focus-visible`. At the very end of `renderDesktop`, after `restoreFocus` and after the `scrollTo` of the `holding` branch (the tile's rectangle is read after the page is put back), if the focused element is that tile's new node (same `data-widget-id`, still `:focus-visible`) and the layers allow a tooltip (normal mode, no drag), `showTooltipFor` runs for it and the focus window of decision 7 opens (the render may scroll). The text is the new node's. The tile must be at least partly inside the window (its rectangle meets the window): a tile that another tab carried wholly out of it gets no tooltip, because the focus is put back with `preventScroll` (nothing scrolls to the tile) and the tooltip would stand against the window edge with no tile beside it; that is what the base did (the render closed the tooltip and nothing brought it back; checkpoint L1-01). A tooltip that was open for the pointer is not restored (the pointer opens it again on the next move); a tile that lost focus, a dialog that took it, edit mode and a drag restore nothing. This holds for every render that starts with such a tooltip open: the weather load at open, a manual or automatic attempt, a re-read on return, a city change. It does not hold for a window resize: the `resize` listener hides the tooltip at once and the render that follows runs a frame later, with nothing to remember (stage 1 SK-01; Accepted exception 3). The re-creation of the focused node itself is not touched.
7. **A document scroll hides the tooltip (148, keyboard scroll).** `onWindowScroll` (the passive `window` listener) first does what the `#favorites` capture listener does: unless the focus window covers it, `hideTooltip()`. The focus window is either the clock (`performance.now() < ignoreScrollUntil`, 250 ms after a focus or after decision 6's show) or a one-shot flag set by the `focusin` handler and by decision 6 and cleared by the next animation-frame callback after it (in the frame's rendering steps the scroll event of the scroll that the focus caused comes before the callbacks of the same frame, so a starved frame cannot deliver it after the 250 ms and hide the new tooltip; the clock stays for a smooth scroll that lasts longer). The window is therefore 250 ms by the clock, not one frame: a real scroll that begins within 250 ms of a focus, or of the render that brought the tooltip back (decision 6), is ignored as well (Accepted exception 12); the acceptance (AS-BC-05) puts at least 400 ms between a focus and the scroll key it expects to hide the tooltip. The existing `wheel` and `touchmove` listeners and the `#favorites` scroll listener stay. A hidden tooltip is shown again by the existing triggers (a pointer over, a new keyboard focus).
8. **The 50/50 footer buttons may shrink (148, S3-01).** `min-width: 0` on `.favorite-form__footer .button` (`src/controls.css`) and `.city-modal__actions .button` (`src/surfaces.css`; the footers of wizard steps 1 and 2 are this selector too, there is no third one), so two buttons of `flex: 1` are equal halves at every font size and never wider than their half. At 16 px and 20 px nothing changes (the content fits, the halves are what they were). The acceptance is in AS-BC-14; the mechanism is the one-line recommendation, confirmed by the stage 1 prototype (P8).
9. **A narrower option padding when the font is enlarged and the window is narrow (148, L2-02).** In `src/surfaces.css`, in a media query `(max-width: 14rem)` (the browser's default font size, as the query at the row stacking; at the default 16 px it is 224 px and never matches, at 24 px it is 336 px, and the bound is included: the rule is on at 336 px and off from 337 px), `.desktop-dialog .segmented__option` gets `padding: 0 4px` (from `0 5px`). Arithmetic from the cited numbers: the last label's slack is `23.6 - 5p` at the 17 px bar, so `p` of 4 gives 3.6 px (the stage 1 prototype measured 3.56); take the smallest reduction that meets AS-BC-15 (3 px if 4 px is not enough, for the radio groups only). The same rule covers every `.segmented` group of the dialogs (Icon, Color, Size, City label); the On tile toggles sit in the same narrow block at `0 5px` today (`surfaces.css`, 599-602), so for them 4 px is a CHANGE too, not a value they keep. Their focus ring (the block "A toggle group": outline 2 px, offset -4 px, so it spans 2 to 4 px inside the option) ends exactly at the text's start when the padding is 4 px: the gap between the ring and the text is 1 px at 5 px and 0 at 4 px, and AS-BC-15 measures it. A 3 px fallback never applies to the toggles. If a toggle fails a measure of AS-BC-15 at 4 px (a negative ring-to-text gap, or the text-to-border distance), the toggles keep 5 px (the selector is narrowed to the radio groups) and the executor records it in the report; it is not a reason to go lower. Nothing changes at 16 px and 20 px.
10. **The screen's alert is spoken once (170 (2)).** When the Reset grid dialog (`confirm-reset-grid`) first opens, `role` and `aria-live` come off the `p` of `.grid-unreadable` (the text stays). No module flag: nothing rebuilds the screen after load (Ruling 9). At first load the paragraph is still `role="alert"`, so the message is announced once as before. The Reset grid button, the dialog, the failure chip (`#desktop-status`, its own alert) and the `newer` screen's alert are unchanged.
11. **A press right after a dialog opened does not move the focus (182).** `openDesktopDialog` adds a `mousedown` listener on the backdrop and on the dialog root: within `DIALOG_BACKDROP_GUARD_MS` (300 ms) of the open, when the target is the backdrop or lies in the dialog but not inside an `input`, `button`, `label`, `select`, `textarea` or `a`, `preventDefault()` is called (the focus stays where `openDesktopDialog` put it). The backdrop's `click` guard, the Reset grid guard and every click handler are unchanged; no flag, timer or constant is added (`desktopDialogOpenedAt` and `DIALOG_BACKDROP_GUARD_MS` exist). After 300 ms a press on the backdrop moves the focus as today. The rule is kept in the one generic function on purpose: the cause is the same for every dialog that a double click on its opener opens (the second press of the double click lands on the backdrop, which the first click has just put over the page): `Add link` from the Add menu, a link or weather tile in edit mode (`edit-link`, `edit-weather`), a Remove or Hide badge (the two confirms); the code gives no place in `openDesktopDialog` where a narrower rule would be simpler than this one. AS-BC-11 therefore checks `Add link`, plus a control on `edit-link` and on `confirm-delete` that nothing else changed; `confirm-reset-grid` has its own press guard (`guardResetDialogPresses`) and stays as it is (`dg-91` unchanged). This supersedes in part the note of `docs/wizard-trap-add-dblclick.md` that the focus after a double click on `Add link` (`body`) is not asserted (AS-WTA-07 and its Accepted exception 3), and its `## Non-goals` 5.
12. **The second press of a swap does nothing (183, Kier's variant A).** The click that moves the Add menu to its second level (`add-weather` in `onAddMenuClick`) records its point and `event.timeStamp` when `event.detail > 0` (a pointer; a keyboard activation records nothing). In the document `pointerdown` listener of the Add menu, after the `!addMenuRoot` return and before its other conditions (the `contains` return and the outside press), a pure rule (`isSwapSecondPress(record, press)`, Ruling 13) decides: a press that falls within 300 ms and 4 px of the recorded click (compared by `event.timeStamp`, `clientX`, `clientY`) while the menu is open (`addMenuRoot`) calls `armPostCloseClickGuard()` and returns: the menu is not closed, nothing is restored, `addMenuDismissPress` is not set, and the guard swallows the `click` of that press, cancels its `mousedown` default and keeps `backgroundPressed` from leaving edit mode (the three Run 57 mechanisms, no new listener). The press may land on the menu or outside it. The record is dropped when the menu closes and is never older than 300 ms when read. A third press is judged by the same rule against the same record: the rule swallows it only within 300 ms and 4 px of the opening click (not of the second press). But a swallowed second press has armed the post-close guard (`POST_CLOSE_CLICK_GUARD_MS`, 300 ms counted from that second press), and that guard swallows the `click` of every pointer press until it ends whatever the rule says. So a third press that is later than the rule's 300 ms but still inside the guard (the second at 120 ms, the third at 350 ms: the guard lasts to about 420 ms) is not an ordinary press: with 1 hidden metric it is an outside press and closes the menu (the `pointerdown` that closes the menu is not guarded); with 2 or 3 hidden metrics it lands on an item of the second level, its `click` is swallowed and nothing is restored (the premise prints what lies under the point). A third press later than that, past the guard (at least about 450 ms after the opening click when the second came at 120 ms), or elsewhere, is an ordinary press. Constants: `ADD_MENU_DOUBLE_PRESS_MS = 300` (the length of the project's other guards, `POST_CLOSE_CLICK_GUARD_MS`, `DIALOG_BACKDROP_GUARD_MS`; a human double click is mostly under 300 ms) and `ADD_MENU_DOUBLE_PRESS_SLOP_PX = 4` (a hand's tremor). Why not 500 ms: the `dg-93` recipe presses the second item of the three-item second level 459.9 and 461.7 ms after the swap click, 0.86 and 0.98 px from it (P10, cited), which 500 ms would swallow; 300 ms leaves it 160 ms outside, so `dg-93` stays green with no change. A press elsewhere, after 300 ms, or more than 4 px away (the first item of the second level, the quick pick of `AS-WTA-06`: with the menu below the Add tile the swap click and that pick are 40 px apart) behaves as today. The distances are a fact of the layout, not of the rule: with the menu above the Add tile an item of the second level can lie within 4 px of the swap point (P10: the last of three, the second of two), and a quick pick of such an item within 300 ms is swallowed like the second press (Accepted exception 14). With three hidden metrics below the tile the second press lands on the second level's item and its click is swallowed (nothing restored, the second level stays open); with one hidden metric it lands outside the shorter menu and does not close it; with a link tile under the point its click does not open `edit-link`.

## Accepted exceptions

1. **A deliberate quick second press is lost (183).** Kier's price of variant A: a press within 300 ms and 4 px of the click that moved the menu to its second level does nothing, so does a third press within 300 ms of that click; a third press later than that is an ordinary press only when it also falls later than, but not in, the 300 ms guard that the swallowed second press armed (AS-BC-12: with the second at 120 ms the guard lasts to about 420 ms, so a third press on a menu item at 350 ms does nothing, and one at 450 ms or later is ordinary); and that post-close guard also swallows any deliberate pointer press in those 300 ms (the same trade as the other guarded closes, `docs/wizard-trap-add-dblclick.md` Accepted exception 1). A double click slower than 300 ms behaves as before (the window was 500 ms in revision 1; Ruling 11).
2. **A press does not move the focus in the first 300 ms of a dialog (182).** A press on the backdrop or on a non-control part of a dialog within 300 ms of its open leaves the focus where it was; clicks (the backdrop's own guard ignores them) and presses on controls are not touched.
3. **A hover tooltip is not restored, and a resize closes the tooltip for good (159).** After a render the tooltip of a keyboard-focused tile returns; one that was open for the pointer stays closed until the pointer moves (`AS-TRR-08`). A window resize hides the tooltip by its own listener, before the render runs; the render restores nothing, and the tooltip comes back only when focus moves away and onto the tile (stage 1 I-3, SK-01).
4. **A scroll hides the tooltip (148).** Keyboard, wheel and scrollbar scrolls hide it; it does not follow the tile.
5. **The alert is not repeated (170).** After the Reset grid dialog first opens, the screen's paragraph is plain text; a screen reader user who comes back to the page without a reload does not hear it again. A real screen reader was not run; the owner's VoiceOver smoke (roadmap, "Только Кир") is the check.
6. **The jiggle starts at an arbitrary phase when edit mode is entered (157).** It is a function of the clock, not of the moment of the click; invisible.
7. **A replay can come after a replay's own cause is gone (154 (1)).** The replay goes through the ordinary guards (`due`, a shown tile, a visible tab, online), so a state that changed meanwhile is respected; the only residue is one request for the stored city after a failure.
8. **Fonts above 24 px stay out (148).** The geometry fixes are measured to 24 px; 32 px and more is outside the project (Kier, 2026-11-15, rows 148 L3-01 and 170 (1)).
9. **The accessibility tree, not a speech output, is measured (170, 184).** `aria-invalid`, `aria-describedby`, `role` and the computed description are asserted; what VoiceOver says is not.
10. **A silent heal on a mutation site only for a partial desk (154 (2)).** The rule is the same at the three heal sites, but a mutation site has Settings in the shown state (edit mode and Add link need tiles that a failed ensure does not leave), so there the reset message stays; a partial desk that shows Add and no Settings heals silently there. That sub-case is proven by the unit test of the pure rule, not by an E2E scenario (it needs a seeded partial desk with an ensure that fails).
11. **The equal-state ensure chip clear may be unit-tested only (154 (4)).** The chip clears before the equal check; the E2E needs a fault that fails only the ensure on a full storage, which the harness lacks (AS-BC-08 (ii)). Without one the branch is covered by the unit test of `hasEverySystemTile` and a source pin of the order.
12. **A scroll in the 250 ms after a focus is ignored (148).** The window of decision 7 is a time (the clock, `performance.now() < ignoreScrollUntil`, 250 ms after a focus or after the render that brought the tooltip back) plus a one-shot flag; neither tells a real scroll from the focus's own. Price: a key scroll that begins so soon after Tab (or after a render restored the tooltip) that its whole animation ends inside the 250 ms leaves the tooltip on screen, away from its tile if the page moved, until the next scroll hides it. A key scroll is an animation, not one event: measured on the harness's Chromium (cited (stage 3 round 3), 80 links, 1784 px document) ArrowDown gives `scroll` events 23 to 156 ms (28 to 143 ms in the lens's run) after the key, PageDown 6 to 157 ms, Space 7 to 158 ms; so only a key pressed within about 90 ms after Tab keeps the tooltip (all events inside the window), and a key pressed 100 to 250 ms after it has its late events after 250 ms hide the tooltip, which is the designed behaviour, not a failure. The cost is therefore visible but narrow: a key within about 90 ms of landing on a tile, which a hand does not do (a script can). `AS-BC-05 (a2)` records it (the first event only). A real Chrome with the operating system's own smooth-scroll setting may animate for another time; not measured. The flag is also not cleared while the tab is hidden (`requestAnimationFrame` does not run there), so the first real scroll after the return is ignored once (the same price).
13. **A manual failure text outlives the replay that follows it (154 (1)).** A manual attempt that fails writes its text into `#desktop-status` for 8 s (`DESKTOP_STATUS_MS`); the replay of decision 2 is automatic: it neither writes that line nor clears it on success, so for up to 8 s the tiles can be fresh while `Couldn't update …` is still up. The alternative (an automatic success clears a non-persistent status line) widens the behaviour of the automatic path and is not taken. The replay announces nothing.
14. **A quick pick within 4 px of the swap point is lost (183).** When the menu stands above the Add tile, an item of the second level can be within 4 px of the opening click (P10, cited (stage 3): the last of three, 0.1 to 0.3 px; the second of two, 0.1 px; one hidden metric: 138.6 px, not affected). A deliberate pick of that item within 300 ms of the click is swallowed like the second press; slower is an ordinary press. The cost of the rule's geometry on top of Kier's variant A; not measured at 500×800 and 320×600 (Task 0).
15. **A render with no live dragged tile is pinned, not driven (134).** The drag-height rule applies only while `reattachDrag` would go on; the state where it would cancel (the dragged tile is not in the new layout) is reachable only by the `gone` outcome over the dragged first metric tile, which costs an E2E recipe for a state of one pointer and one tile. It is covered by a source pin that both use the same condition and by the reading of `reattachDrag`.
16. **A two-line footer label starts 1 px inside its button's top edge (148, S3-01).** At 24 px in a 320 px window the `Reset grid` confirm's label wraps onto two lines and its button grows (52.4 px against Cancel's 40 px); the first line's box starts 1.0 px under the border edge (the line box, not the ink). AS-BC-14 holds the 2 px threshold on the horizontal axis and asks only that every line lie inside the button on the vertical one, as `docs/unreadable-grid-reset.md` AS-UGR-07 and its Accepted exception 14 already do; no CSS beyond decision 8 is added for it (cited (stage 3 round 3), P8).
17. **The edit-mode and drag guard of `restoreKeyboardTooltip` is pinned, not driven (159).** The guard `if (desktopUi.editMode || dragSession) return;` is unreachable in the E2E: in edit mode (and during a drag) no tooltip is shown, so no render has a keyboard tooltip to remember (`keyboardTooltipTileId` returns null before the guard). It is closed by the `newtabSource` pin of decision 6 and by the reading of `showTooltipFor`; the same shape as exception 15.
18. **A render in the same frame as the `focusin` does not bring the tooltip back until the next focus (159).** The `focusin` handler shows the tooltip in an animation-frame callback; a render that runs after the `focusin` and before that callback finds no shown tooltip (`keyboardTooltipTileId` is null), remembers nothing and hides nothing that was shown, and the callback then shows the tooltip for the old node, which the render replaced (`document.activeElement === trigger` is false for it), so nothing is shown until focus moves away and onto the tile again. The window is about one frame (16 ms); accepted.
