## Terms

- **Return**: a `visibilitychange` event on `document` when `document.visibilityState` is `"visible"` (the tab came to the front, the window was restored, the screen woke up).
- **Due** (weather): the shown weather is an error, is stale, or is `ready` but its data is 30 min old or older (decision 2).
- **Attempt**: one `weatherService.initialize()` call under the 15 s `withTimeout`, as the retry press makes it (`retryWeather`). **Automatic attempt**: the same attempt started by a return or an `online` event.
- **Re-read** (grid): reading the widgets state from `chrome.storage.sync` again and showing it (decision 5).
- **Layer**: anything that owns the screen while it is up, so the grid must not change under it: an open desktop dialog, edit mode (with its Add menu), a drag (started, or settling after the drop), the city modal, the first-run wizard, a write in flight (`favoritesBusy`).
- **Pending re-read**: a return that arrived while a layer was up; it runs once, after the last layer is gone (decision 6).

## Decisions

1. **One tab-return handler, two listeners, no timers.** `newtab.js` registers once, next to the other page listeners: `document.addEventListener("visibilitychange", …)` and `window.addEventListener("online", …)`. Both handlers return at once unless `document.visibilityState === "visible"`. A change to `hidden` does nothing. The listeners do nothing at load: the boot path, its reads and its requests are as on `main`. No `setInterval`, no new `setTimeout` for scheduling, no `pageshow`, `focus` or `storage.onChanged` listener. The visibility is read only from `document.visibilityState`. Suggested names: `onTabVisibilityChange`, `onBrowserOnline`. A return does two independent things: the weather (decisions 2–4) and the grid (decisions 5–7).

2. **When the weather is due (item 11, decision of Kier).** A pure function `weatherRefreshDue(result, now)` in `weatherUiState.js` takes the shown result (`effectiveWeatherResult()`, so a city change in flight, which shows loading, is not due) and answers `true` when `result.status` is `"error"` or `"stale"`, or is `"ready"` and `result.data.fetchedAt` is a finite number with `now - fetchedAt >= WEATHER_CACHE_TTL_MS` (30 min, the cache rule of `weatherService.js`: the constant moves to a new shared-constants module `src/weatherShared.js` (as `favoritesShared.js` and `widgetsShared.js` hold theirs), which `weatherService.js` and `weatherUiState.js` both import, so the pure UI-state module does not depend on the service that pulls in the HTTP client; one definition; a cache is fresh while `now - fetchedAt < 30 min`, so exactly 30 min is due). It answers `false` for a missing result (loading, or the boot load still in flight), for `no-location`, for a `ready` result younger than 30 min, and for a `fetchedAt` that is missing, not finite or in the future (the clock moved back). **Ruling (марафон, на проверку Киру): a tab that shows the "Set a city" hint is not refreshed (no data that could be old); a city set or changed in another tab appears on the next action or reload, or when a refresh is due and re-reads the stored city, as today; альтернатива: treat `no-location` as due (a storage read, no request): the hint would disappear on return when another tab set a city; цена ошибки: one condition plus one AS, nothing structural.** When a refresh is due and runs, `initialize()` re-reads the stored city itself, so a city changed in another tab is picked up then (its result carries the new `location`).

3. **The automatic attempt is the retry attempt (item 11).** `retryWeather` gets an options object, `retryWeather({ automatic = false, ignorePause = false } = {})`; the click branch keeps calling `retryWeather()` and the behaviour of the manual path does not change. With `automatic: true` the entry gate is `weatherService` present and `weatherRefreshDue(effectiveWeatherResult(), Date.now())` instead of "status is error or stale"; `startWeatherRetry(weatherUi, now, { ignorePause })` takes the same in-flight guard and 3 s pause (the pure function gets the optional third argument; with `ignorePause` only an attempt in flight blocks); everything after the gate is the existing code: the token, the generation bump, the busy render, `withTimeout(weatherService.initialize())`, the outcomes (`updated`, `gone`, `failed`), the drop of a late answer by the token and the generation, the pause timer and its silent end. Consequences by design:
   - An **error or stale tile** shows the existing busy state while the attempt runs (`data-retry="retrying"`, `…` on an error tile, the spinning glyph, `Trying again…`); a **ready** tile shows nothing while it runs (it has no retry control and the model's `retry` is `null` for it), so an attempt whose shown result is `ready` does not render at its start (nothing would change, and a render would hide a tooltip under a resting pointer for nothing); the tiles change when the answer arrives.
   - One attempt serves all tiles and a manual press, a return and an `online` event share one in-flight guard: they can never run in parallel (one forecast plus one air-quality request per attempt).
   - A failed attempt on a ready tile depends on how it fails. **A fast failure** (the service answers: the request fails at once) gives the service's own `stale` result (the cache plus the error), so the tile becomes the honest stale tile with `Updated N min ago`. **A timeout or a throw** (`withTimeout` rejects after 15 s, or `initialize()` throws) replaces nothing, as for every attempt (`retryWeather` keeps the shown result): the tile stays as it was (`ready`, the old values, no stale marking, no busy marker), the pause starts, and the tile is still due at the next return. The answer of a timed-out attempt may still arrive later and write the cache (the service is not cancellable): the tiles do not change then, and the next return or press finds a fresh cache and makes no request (Accepted exception 17). The guard "a failed read never downgrades a tile that still has data" (`downgrade` in `retryWeather`) widens from `weatherResult?.status === "stale"` to `weatherResult?.data` (a `ready` or `stale` result): an `error` result from the service does not replace values that are on the tiles.
   - The failure starts the usual 3 s pause (the retry glyph dims and the end of the pause is silent, `endWeatherRetryCooldown`).
   - The `gone` outcome (the city was removed in another tab, `initialize()` answers `no-location`): the hint tile replaces the metric tiles as in the retry spec, the status line is not touched, nothing is announced, and focus moves to the hint tile only if it was on a weather tile when the attempt started (read before the first render); a returning user whose focus is on `body` keeps it there. The manual press keeps its existing rule (focus to the hint tile when focus is on `body` afterwards).
   - **The automatic attempt is silent.** It never writes `#desktop-status`, never calls `announce`, in no outcome (success, failure, `gone`), and never clears an existing status text either (the status line belongs to the user's own actions). No `Weather updated`, no failure text, no new string. **Ruling (марафон, на проверку Киру): the weather refresh and the grid re-read that only change what is drawn are silent for the screen reader and the status line (a heal keeps its existing message, decision 7); альтернатива: announce `Weather updated` politely as a manual retry does, and `Grid updated` after a re-read; цена ошибки: one or two strings, one `announce` call each, plus their AS; a screen-reader user would then hear a message each time they come back and something changed.**
   - In **edit mode** the attempt runs and renders into the Edit buttons exactly like an attempt that was started before edit mode was turned on (`docs/weather-tile-retry.md` decision 12): the Edit buttons carry `aria-busy` and the description `Trying again…` while it runs (Accepted exceptions).

4. **Triggers (item 11).** `onTabVisibilityChange` on a return: `if (navigator.onLine !== false) void retryWeather({ automatic: true })`, and the grid re-read of decision 5. `onBrowserOnline` when visible: `void retryWeather({ automatic: true, ignorePause: true })`. **Ruling (марафон, на проверку Киру): a return does not try while the browser says it is offline (`navigator.onLine === false`; the `online` event comes later), and an `online` event ignores the 3 s pause after a failed attempt (the network has just come back); an attempt in flight still blocks both; альтернатива: attempt on every return even offline, and let `online` wait out the pause; цена ошибки: an offline return flashes `Trying again…` and two failing requests; a wake-up whose `online` arrives within 3 s of the failed first attempt leaves the tiles in error until the next return or a press.** Reasoning for the second half: on wake from sleep the visibility event comes first, the network a second or two later; the first attempt fails at once and its 3 s pause would swallow the `online` event, the only signal that the network is back. `online` while the tab is hidden does nothing; the later return finds the data still due. `navigator.onLine === true` proves nothing about a connection, so a failing attempt while "online" is the manual retry's failure (same pause, no text).

5. **The grid re-read (item 13, decision of Kier).** `refreshDeskOnReturn()` on a return, in this order. The choice "do it, keep it for later, do it again, or leave it" is one pure function, `deskRefreshDecision({ hasState, locked, drawn, blocker, startedFrom, current })` in `desktopUiState.js` next to `deskRefreshBlocker` (decision 6), returning `"skip"`, `"pending"`, `"again"` or `"apply"`: `"skip"` when there is no state to refresh (`hasState` false: `widgetsService` missing or `widgetsState` is `null`, the boot read produced none) or the grid is locked read-only (`locked`: `widgetsNewer`); else `"pending"` when the grid has not been drawn yet (`drawn` false, `renderedColumns === 0`, the guard the `resize` handler uses: between the boot read of the state and the first render the page still reads the city and the local wizard flags, and nothing may be painted before the wizard decision) or a layer is up (`blocker` is not `null`); else `"again"` when `current !== startedFrom` (the `widgetsState` object now is not the one the re-read started from: this tab's own state changed while it was reading); else `"apply"`. The order of those tests is the order of the list.
   1. Entry: the decision with `startedFrom = current = widgetsState`. `"skip"`: stop, nothing remembered. `"pending"`: set the pending flag and stop (the flush of decision 6 runs it after the first render or after the last layer). `"apply"`: the re-read starts, and the start **consumes** the pending flag (step 2 and the flags paragraph below).
   2. At most one re-read runs at a time (the "running" flag is set when it starts); a return whose entry decision is `"apply"` while one runs queues exactly one more after it ends (never two in parallel; any number of returns during one read make that one queued re-read). The queued one starts through this same entry, so a layer that opened meanwhile postpones it again. The same queue takes an `"again"` result (step 5).
   3. Read the raw meta (`syncStorageArea.get(WIDGETS_META_KEY)`) and `inspectWidgetsMeta` it. `newer` or `invalid` (a version above ours, or any meta that is not a valid v3 one): **stop, nothing written, nothing drawn, no message** (the unreadable-data state is run 51; the next mutation shows the existing refusal through `assertWritable`). `missing` and `valid` go on. A read that fails, whether it rejects or throws synchronously (a lost extension context throws from `chrome.storage…get(...)` itself instead of rejecting), ends the re-read silently: no message, no write, no render.
   4. `widgetsService.getState()` (no lock, as the boot read; a read can see a state in the middle of another tab's two-call write, which the next return corrects, Accepted exceptions). A rejection or a synchronous throw ends the re-read silently as in step 3 (no message: the next action reports a storage problem). Nothing has been written up to here.
   5. The decision again, now with the `startedFrom` of step 1 and the current `widgetsState`. `"skip"` and `"pending"` as in step 1 (a layer the user opened during a slow read wins; the result is thrown away, nothing is lost because nothing was written). `"again"`: the result is older than what is drawn, it is thrown away and the queued re-read of step 2 follows, so an older read can never overwrite a newer write of this tab.
   6. `"apply"` (decision 7). There is no `await` between this decision and the render of a healthy state. A state without Settings (another tab cleared the storage) is healed first, under the busy lock exactly as `recoverFromGoneLink` does it (`startFavoritesAction({ render: false })`, `healClearedDesk(state)`, `finishFavoritesAction(generation, …)`): `ensureWidgetsLayout` for the first screen of now, a second read, the weather city dropped when the storage has none, under the rules of `docs/stale-tab-empty-state.md` and `docs/stale-tab-recovery-followups.md`. The heal starts only after the decision said `"apply"`, so a result that was thrown away never leaves a heal half-shown (no lost `Your layout was reset in another tab.`, no city kept in memory without its render); while it runs the writes of the user are refused by `favoritesBusy` (edit mode can still be toggled; the heal's result is applied regardless, as in `runDesktopMutation`, which has the same window). This is the only write a re-read can make. No new direct `firstScreen(` call (the existing pin that counts three stays true).
   The re-read has no timer of its own and takes no busy lock for its reads (a write of the user starts only from a layer, see decision 6); only the heal takes it.
   **The lifecycle of the flags** (names suggested: `deskRefreshPending`, `deskRefreshRunning`, `deskRefreshQueued`, `deskRefreshFrame`):
   - `deskRefreshPending` is set only by a decision `"pending"` (at entry or at step 5). It is cleared at the moment a re-read passes the entry decision with `"apply"` and starts: the start consumes it, and step 5 may set it again. So a return that arrives between the close of a layer and the flush frame finds no layer, starts at once and consumes the flag, and the frame then finds nothing to do: one re-read, not two.
   - `scheduleDeferredDeskRefresh()` reads the pending flag synchronously and schedules a frame only when the flag is set and no frame is scheduled (a render or a close with nothing pending costs nothing). The frame looks again at the flag and at `document.visibilityState === "visible"` and, if both hold, calls the common entry, which decides again; a hidden tab leaves the flag set and the next return consumes it.
   - `deskRefreshRunning` and `deskRefreshQueued` are cleared in a `finally` that covers every way out: a stop (`"skip"`, `"pending"`, a `newer` or `invalid` meta), a rejected or synchronously thrown read, a discard (`"pending"`, `"again"`), and `"apply"`. After it, if a re-read was queued, it starts once through the entry. A failed read therefore leaves nothing stuck: the next return reads again, and a single failure never switches the re-read off in that tab (AS-TRR-10 (f)).

6. **Layers postpone the re-read (item 13, decision of Kier), and it runs once afterwards.** A pure function `deskRefreshBlocker(state, { cityModal, onboardingWizard, busy, dragSettling })` in `desktopUiState.js` (next to `escapeLayer`) returns the name of the first layer found, or `null`: `"drag"` (`state.drag`, or `dragSettling`), `"dialog"`, `"cityModal"`, `"onboardingWizard"`, `"menu"`, `"editMode"`, `"busy"`. The blocker is checked at the return and **again after the awaits of the re-read, right before it applies** (a layer the user opened during a slow read wins): a re-read that finds a layer up throws its result away and sets the pending flag. A second guard covers the one writer that needs no layer: the background accent write of `refreshAutoAccent` (three callers: the Finish of the first-run wizard, Add link, and Edit link with the Auto color; it writes the item and replaces `widgetsState` when the favicon has been sampled, with no busy lock). It is the `current !== startedFrom` test of `deskRefreshDecision` (decision 5): a re-read that started from one `widgetsState` object and finds another when it is about to apply is thrown away and re-run once. The pure function is what tests this guard (a unit table); an E2E run cannot place the two events in that order with the harness (AS-TRR-10 (e)). **Ruling (марафон, на проверку Киру): besides the three layers Kier named (dialog, edit mode, drag) the re-read also waits for the city modal, the first-run wizard and a write in flight; альтернатива: only the three named layers; цена ошибки: the grid could be redrawn under an open city modal or wizard (their desk is inert and veiled, so nothing is lost visually) or beside a write in flight (the write's own result is the freshest state anyway); one entry fewer in the predicate and its table.** The pending re-read **starts once, within one animation frame after the last layer is gone (or after the first render, when the return came before it)**, and only while the tab is visible (the frame checks `document.visibilityState`; a hidden tab keeps it pending and the next return consumes it, AS-TRR-09 run 9; the lifecycle of the flags is in decision 5). Two returns during one layer make one re-read. The `"drag"` and `"menu"` entries are absorbed by `"editMode"` in every state the page can reach (a drag and the Add menu exist only inside edit mode, and the real browser cancels a drag on the `blur` of a hidden tab, which the visibility stub does not fire), so no E2E run sees them alone and the unit table separates them; AS-TRR-09 run 4 holds the predicate on the stub. The `"busy"` entry of the predicate is a defence that no E2E run can see alone: a write in flight always has its dialog (or the wizard, or edit mode with a drop) still up, which the predicate names first; the unit table holds it. Layers nest and the re-read waits for the last one: a drag and the Add menu exist only inside edit mode, the Edit link, Edit weather and confirm dialogs are opened from edit mode (closing them leaves edit mode on), the city modal can stack over the Edit weather dialog; only the Add link dialog (the Add tile in normal mode), the city modal from the hint tile and the wizard stand alone. A layer that ends with its own write (Save, Delete, Hide, a drop that writes) already shows the freshest state, because every mutation reads storage first, and the pending re-read that follows finds nothing to change and draws nothing (decision 7). Implementation shape (the plan may adapt it; the contract above is what is tested): `scheduleDeferredDeskRefresh()` called at the end of `renderFavorites()` (every end of edit mode, drag and write ends in a render) and of `closeDesktopDialog`, `hideCityModal`, `hideOnboardingWizard` (these close without a render), which checks the flag and the blocker one `requestAnimationFrame` later.

7. **Applying the state.**
   - **Equal means nothing happens.** The fresh state (after the heal) is compared with `widgetsState` by value (a pure `isSameValue(a, b)` in `storeUtils.js`, deep equality independent of key order, arrays in order). Equal: no render, no DOM change at all inside `#favorites` (the tile nodes keep their identity, focus, hover tooltip, scroll position and running animations), no status text, no announcement. This is the common case and it must be invisible.
   - **Different:** `widgetsState = fresh; renderFavorites()`: the one render path, a pure function of the stored grids and the current column count (so a window that was resized meanwhile is laid out for its size now, nothing is written). If focus is on a tile when the re-read applies and that tile is gone from the fresh state, focus goes to its neighbour by the existing rule of a deleted tile (`neighborTargets`: next tile in DOM order, else previous, else Settings, read from the old DOM before the render) with `preventScroll`, never to `body`; focus anywhere else (body, a field) is left alone. A render that shrinks the page below the scroll position clamps `scrollY` as a delete does (`docs/drag-scroll-target.md` Non-goals; Accepted exceptions).
   - **After a heal** (decision 5 step 6) the grid is always rendered (the weather city may have been dropped too) and the existing neutral message `Your layout was reset in another tab.` (`LAYOUT_RESET_MESSAGE`, info tone) is shown; a failed heal (the final state has no Settings: a rejected write or a failed second read) runs `leaveEditModeAfterFailedHeal()`, renders, and shows the existing persistent chip `Couldn't restore your layout. Reload this tab.` with its Reload button and focus on `#favorites` (`showLayoutRestoreFailure`), as after a write. **Focus after a heal:** if focus was on a tile of the grid when the heal ran (that tile is gone with the cleared storage), it goes to Settings, forced (`focusWidgetTarget([SETTINGS_TILE_ID], { preventScroll: true })`, as `recoverFromGoneLink` does: a neighbour list read from the old DOM would find a just-created tile first); focus anywhere else is left alone; it never falls to `body`. These two are the only messages a re-read can show; a re-read that only changes what is drawn says nothing (Ruling in decision 3).
   - `widgetsState` is replaced only by a result of storage: an attempt of the weather and a re-read never touch each other's state.
   - **Vocabulary.** The code reuses `neighborTargets`, `focusWidgetTarget` and the existing selector constants and adds no string literal that contains `widget` or `desktop`: the allowlist of `test/vocabulary.test.js` is global by exact literal and AS-TRR-13 requires no new entry.

8. **Nothing user-visible is added.** No new string, element, attribute, class, token, setting or storage key. The messages are the two that exist. New string literals in `src/*.js` obey `test/vocabulary.test.js` (no banned words, no hyphen dashes). ## Accepted exceptions

1. **No timers.** A tab that stays visible keeps its weather, its age sentence and its grid until the next return, press or action (decision of Kier). A tab that is never hidden (a second monitor) is never refreshed.
2. **Torn read.** The re-read is not under the mutation lock (as the boot read). It can see another tab's two-call write (items, then the meta) half done and show a mix of old order and new items; the next return corrects it. A heal started from such a read only fires when Settings is missing, as at every boot.
3. **Heal without a user action.** A return can write the six system keys (only when the state has no Settings), under the existing rules; Chrome Sync delivering keys in pieces to a second device can look like that for a moment (the same exposure as the `ensureWidgetsLayout` of every new tab; run 51 owns the Sync edge cases).
4. **A shrinking page.** A re-render on return that makes the page shorter than the scroll position clamps `scrollY` as a delete does (`docs/drag-scroll-target.md` Non-goals).
5. **Weather during a drag.** An automatic weather result can still arrive while a drag runs (as a boot or retry result can; backlog 134): the existing `reattachDrag` handles the render, the known scroll nudge at the bottom of a drag grid is not made better or worse.
6. **Edit mode.** An automatic attempt in edit mode shows `aria-busy` and `Trying again…` on the Edit buttons while it runs, as an attempt started before edit mode does.
7. **`navigator.onLine`.** Only `false` is trusted; with `true` an attempt may still fail (no route to the service), with the same pause and no text.
8. **`online` flaps.** Each real `online` event starts an attempt (it ignores the pause); a flapping network is bounded by the in-flight guard and the 15 s guard, nothing else. An `online` that arrives while an attempt is already in flight is dropped by that guard: Chrome may cancel the in-flight requests about when it sends `online`, so the event can come before the failure of the same attempt, and then the tiles stay in error until the next return or press (the same as `main`, which reacts to nothing; no `online` is remembered, R1-03).
9. **A city set, changed or removed in another tab** shows only when a refresh is due or on the next action (Ruling in decision 2). Until then a tab keeps the old city's values, its 2×2 city line and the city field of an open Edit weather dialog; an automatic attempt that changes `weatherLocation` while that dialog is open does not update the field (R1-08). When the storage is cleared in another tab and healed by a third, a tab that did not heal shows the healed grid on its return but keeps the metric tiles of the old city until a refresh is due (that attempt gives `no-location` and the `Set a city` hint), because `dropCityClearedElsewhere` runs only inside a heal (checkpoint r1, S1-01).
10. **A grid with an unreadable or newer meta** is not drawn differently on return (run 51).
11. **A dialog open on a link that another tab deleted** is not closed by the return: the re-read waits for it, and Save then goes through the existing `LinkGoneError` recovery.
12. **Back navigation** reloads the page (no bfcache restore observed), so a page restored from the cache without a `visibilitychange` is not a case.
13. **Weather is not postponed by layers.** Kier's postponement rule names the grid; an automatic attempt can start and render the tiles under an open dialog or modal (their desk is inert) or in edit mode, as a boot or retry result can (AS-TRR-06 (f) to (h) hold what is promised there).
14. **A failed heal repeats.** After a failed heal the state still has no meta, and `getState()` returns a fresh initial state with new timestamps at each read, so it is never equal to the drawn one: every later return retries the heal (a render, a new chip, focus on `#favorites`) until it succeeds or the tab is reloaded. This is the wanted self-repair (R1-06).
15. **The reset message after a failed boot ensure.** A tab whose boot `ensureWidgetsLayout` failed (`ENSURE_FAILED_MESSAGE`, no Settings) is healed by a later return like a cleared storage: success replaces the persistent boot message with `Your layout was reset in another tab.`, which is inexact there (no other tab did it); a failure replaces it with the failed-heal chip; a chip dismissed with Escape comes back with the next failed return. Rare (a sync write that fails at boot and later succeeds). The alternative, a silent heal when `widgetsEnsureFailed` is set, is not taken (R1-07, L0-02).
16. **A status text can outlive an automatic success.** A failure text written by a manual press stays 8 s; an automatic success in that window refreshes the tiles but never clears the text, which the manual path would (Ruling in decision 3: the status line is for the user's own actions; R1-09).
17. **A late answer after the 15 s guard writes the cache.** The service call is not cancellable (`docs/weather-tile-retry.md`, Accepted exceptions: "A late answer after the 15 s timeout may still write the weather cache"): the tiles do not change when it arrives, but the next return or press finds a fresh cache and makes no request (AS-TRR-06 (b1), (b3); R1-01).

## Non-goals

- Timers, periodic refresh, backoff, a "last updated" time, a refresh of the age sentence while the tab stays visible, a force refresh that bypasses a fresh cache (item 12, closed).
- `chrome.storage.onChanged`, `pageshow`, `focus` and `blur` triggers, `Page Visibility` for background tabs (a hidden tab starts no attempt), a refresh of a hidden tab.
- Any change to tile faces, the retry control, the pause value, the 15 s guard, the 30 min cache rule, the classified texts, the age sentence, the heal helpers and their messages.
- The unreadable-grid screen and Reset (run 51), Chrome Sync partial arrival, the weather-during-drag scroll nudge (backlog 134).
- A new message or announcement for a re-read or an automatic attempt (Ruling in decision 3).
- Any storage change, new key, new permission, new text, new control.
