## Terms

- **Unreadable**: the stored widgets meta is `invalid` in the sense of `inspectWidgetsMeta` (`src/widgetsStore.js`): present and neither a valid version 3 meta nor a meta of a newer version. That includes a malformed meta, a value that is not an object, and a version 1 or 2 meta of an older build (decision 3 of `docs/remove-migrations.md`). `newer` is not unreadable: it is a rollback case and keeps its own message.
- **The screen**: the page content for an unreadable meta (decision 4): one line of text and one button.
- **Reset**: removing the widgets meta and every `quietTabWidget:<id>` key from `chrome.storage.sync`, then loading the page again so that the normal first load runs (decision 6).
- **The default block**: the six system tiles; **the island**: the six tiles plus the starter links after the onboarding Finish (`docs/post-onboarding-grid.md`); **the first screen**: `viewportRows(clientHeight, clientWidth)` rows (`docs/vertically-centered-defaults.md` decision 2).
- **L1-02**: the open finding of the run 40 final design review (lens 1) that the page for an unreadable meta says nothing; it became the accepted exception of `docs/remove-migrations.md` and is the second half of backlog item 95.

## Decisions

1. **What the run does.** Three independent changes of the same page boot, in the order of the tasks of the plan: (a) the ceiling for the first block (decision 2, item 43); (b) the removal of the `tileSize` tolerance (decision 3, item 94); (c) the screen for an unreadable meta with Reset grid (decisions 4 to 8, items L1-02 and 95). Item 44 changes nothing (Accepted exception 1).

2. **The ceiling for the first block (item 43).** `centeredDefaultRow(rows, blockRows)` returns `min(MAX_CENTERED_ROW, max(0, floor((rows - blockRows) / 2)))` with a new exported constant `MAX_CENTERED_ROW = 4` in `src/desktopLayout.js`: **4 is the row the centered rule gives in a 1280×800 window** (`viewportRows(800, 1280) = 9` rows, one-row block, `floor((9 - 1) / 2) = 4`; a unit test pins the equality, so the constant cannot drift from its meaning). Consequences, all by that one function, which both callers share:
   - the default block of a fresh install, a heal of a cleared storage (`healClearedDesk` reads the first screen again) and the first placement by `placeMissing` with all six absent take at most row 4; windows up to 880 px high at width 1280 (`R` up to 10) keep today's rows (`Y0` = 4, 3, 3, 2, 1, 1 at 800, 700, 600, 500, 400, 300; 4 at 880), windows from 960 px (`R = 11`) up are capped (today 5, 6, 8, 12 at 960, 1080, 1440, 2160); a two-row block of a narrow window (500 and 320 px wide) is capped at its top row 4 (rows 4 and 5);
   - the island of the onboarding Finish (`islandPlacements`, `dy = centeredDefaultRow(rows, H)`) is capped the same way: `dy <= 4`, so an island of up to 5 rows ends at row 8 at the latest, which is the last row of a 1280×800 window (`H` is 3 to 5 for every `k`);
   - a block is therefore fully inside the first screen of every window that has at least 5 rows (a one-row block, 424 px at width 1280; 6 rows for the two-row block of a narrow window); a window that is lower still shows it by scrolling, as for any tile that sits below the fold.
   Nothing else moves: the partial self-heal (1 to 5 ids) keeps the row-0 rule, `placeNew` and a restored metric keep the first row with a free cell, a stored `y` is never recomputed (decision 6 of `docs/vertically-centered-defaults.md`), a block already stored at row 5 or lower stays where it is (no migration).
   Ruling (марафон, на проверку Киру): the ceiling is the constant row 4 for every block height and it applies to the island of the onboarding Finish too; альтернатива: a ceiling per height (the row at which that block would be centered at 1280×800: 4 for the default block, 2 or 3 for an island of 4 to 5 or 2 to 3 rows) or no ceiling for the island (the island stays centered in a tall window and has the same Chrome Sync problem); цена ошибки: with the constant an island sits about as high as the alternative would put it and a tall window shows the block above its middle by design; with a per-height ceiling a narrow window at 800 px (R = 10, rows 4 and 5 today) would move up one row, which nobody asked for.

3. **No legacy `tileSize` (item 94).** A stored `tileSize` is ignored data, like the keys of `docs/remove-migrations.md` decision 2: not read, not validated, not written, not removed. Removed: `isOptionalTileSize` and its two uses and the comment above `isWeatherMetricItem` (`src/widgetsStore.js`), the `TILE_SIZES` import there and the export in `src/favoritesShared.js`, the `tileSize` branch of `sizeOf`, the two `delete ….tileSize` lines of `src/widgetsService.js`. Consequences, all for an item that carries the field (the only profiles are development profiles): a value that is not `square` or `wide` (`"huge"`) no longer makes an item invalid (it is read like any item); an item without a valid grid and with `tileSize: "wide"` is no longer 2×1 by that field. **`sizeOf` replaces the branch by the default size of the item**: its valid grid, else a weather metric's `defaultSize(id)` (2×1 for precipitation and air quality, 1×1 for temperature and UV), else 1×1. Reason: a metric has one default footprint everywhere else (`ensureWidgetsLayout`, the restore from Add, `placeholderGrid` in `src/widgetsService.js`), so a metric whose cell is broken keeps the size it has on a normal desk, and what `dg-28` shows today (the broken precipitation tile at 2×1) stays true without the legacy field. The seeds of the harness that carry `tileSize` lose it: `legacyFavorite` (default `tileSize: "square"`), `metric()` and `DEFAULT_SIZES` (they feed the old-data seeds of `dg-81` and `dg-14`, which are compared byte for byte and never read as a layout, so the shape need not be period-exact); `favV2` stops stripping it; `dg-28` drops `{ tileSize: "wide" }` from its metric (the broken grid `w: 5` stays: the tile is still unplaced and, by `defaultSize`, still 2×1, so its expected cell and the dialog's selected size do not change); `09-weather-ensure` AS-2 partial drops the field from its orphan seed and checks `enabled === false` and an unchanged item instead. Unit tests that pin the tolerance are rewritten (`## Affected earlier scenarios`).

4. **The screen (items L1-02, 95).** When the boot finds an unreadable meta, the page draws the screen instead of an empty grid, and does nothing else.
   - **When.** In the bootstrap of `newtab.js`, after the early `newer` check (which still wins) and before `ensureWidgetsLayout`: `inspectWidgetsMeta(rawMeta) === "invalid"` sets a new flag `widgetsUnreadable`, calls `renderFavorites()` and returns, the same shape as the `newer` lock. The early read may fail (`rawMeta = {}`, decision 6 of `docs/remove-migrations.md`); then the meta is read again by `ensureWidgetsLayout`, which already reports it: a result with `meta === "invalid"` takes the same exit (flag, render, return) before `getState()`. `widgetsState` stays `null`, so the tab-return re-read has nothing to refresh (`deskRefreshDecision` says `skip`), the first-run wizard cannot open (no enabled metric) and nothing is fetched (no `startWeather`), exactly as for `newer`. Nothing is written by the boot (zero `sync.set`, zero `sync.remove`).
   - **What.** `renderDesktop` gets a branch after `widgetsNewer` and before `!widgetsState`: `favoritesRoot.replaceChildren(block)` where `block` is a `div.grid-unreadable` holding (1) `createStatus("Your grid couldn't be read.", { error: true, live: "assertive", full: true })` (a `p.status.status--error.status--full[role=alert][aria-live=assertive]`, the same element and the same danger color as the newer-version message) and (2) `button.button[type=button][data-grid-action="reset"]` with the `refresh` icon and the visible text **Reset grid** (accessible name `Reset grid`). No `.desktop-grid`, no tile, no Settings or Add, no other text. `#favorites` keeps `aria-label="Grid"` and `data-edit="false"`.
   - **Where (Ruling).** The block is centered in the window horizontally and vertically (`display: flex; flex-direction: column; align-items: center; justify-content: center; gap: var(--space-grid-12)` inside `.desktop`, `min-height` the window minus the desk padding, text centered; `.grid-unreadable .button { width: auto }` so that the shared "full width below 601 px" rule does not stretch it). At 1280×800 the block center is the window center (400 px) and the page does not scroll; a window lower than the block (under about 100 px) scrolls like any page. Ruling (марафон, на проверку Киру): the screen is a centered block; альтернатива: top left under the desk padding like the newer-version message (a status line with a button below it); цена ошибки: with the centered block a change of mind costs one CSS rule; top left would leave a destructive button in a corner of an otherwise blank window, farther from where a person looks.
   - **Not for `newer`.** A meta of a newer version keeps its text, its read-only lock and no button (a newer build wrote it and this build must not erase it; the answer is to update, as the text says). `docs/remove-migrations.md` decision 3 stays.
   - **The advice of `INVALID_WIDGETS_MESSAGE`** ("Your saved grid could not be read, so changes are paused. Reload this tab; if this keeps happening, update Quiet Tab.") is not changed: the reload now leads to the screen, which is what makes the advice true (item 95).

5. **The confirmation.** A click or an activation of the screen's button opens a desktop dialog of a new kind `confirm-reset-grid` (added to `DIALOG_KINDS`; opened through `openDesktopDialog`, so `#favorites` is inert, the backdrop, the focus trap, Escape and the backdrop rules of every confirm dialog hold) with:
   - title `Reset grid?` (`h2.desktop-dialog__title`), body `Your links will be removed.` (`p.desktop-dialog__body`, `aria-describedby` of the dialog), no error slot;
   - the footer, two 50/50 buttons: **Cancel** (`x` icon, `data-favorite-action="cancel"`) and **Reset grid** (`button.button--danger`, `refresh` icon, `data-dialog-action="reset-grid"`);
   - focus on opening: Cancel (the first enabled button, as in every confirm dialog);
   - Cancel, Escape and a backdrop click (after the existing 300 ms backdrop guard) close it, write nothing and return focus to the screen's Reset grid button (looked up by `data-grid-action="reset"` at close time: a render may have replaced the node);
   - **a double click must not confirm.** The dialog is centered like the screen's block, so the lower right part of the screen button lies under the dialog's own Reset grid button (Live measurement). For the first 300 ms after the dialog opened (`DIALOG_BACKDROP_GUARD_MS`, the value the backdrop already uses) a **pointer** click (`event.detail > 0`) on either of its two buttons does nothing; a keyboard activation (`detail` 0) is not delayed. After 300 ms the dialog behaves as any other confirm dialog.
   - **While the removal runs** (decision 6) the dialog carries `aria-busy="true"` and ignores Cancel, Reset grid, Escape and the backdrop (the existing `favoritesBusy` rule); no visible busy look (the delete confirm has none).

6. **The reset.** A new function `resetUnreadableWidgets(storageArea)` in `src/widgetsStore.js`, next to `ensureWidgetsLayout`, runs under the same extension-wide lock (`withWidgetsMutationLock`):
   - it reads the meta key and runs `inspectWidgetsMeta`; **only `invalid` is erased**. For `valid`, `missing` or `newer` it removes nothing and returns `{ reset: false, meta: <kind> }`: another tab already reset or fixed the data, and a Reset grid pressed on an outdated screen must never erase a grid that is readable now;
   - for `invalid` it reads all keys of the area (`get(null)`) and calls `remove` **once** with `quietTabWidgetsMeta` and every key that starts with `quietTabWidget:` (the item keys that the unreadable meta does not list included; with an unreadable meta `order` cannot be trusted, and a leftover item key would come back through `ensureWidgetsLayout`, which reads `quietTabWidget:<system id>` directly), and returns `{ reset: true, meta: "invalid" }`. A failing `remove` rejects and removes nothing (one call);
   - **nothing else is erased**: the city (`quietTabWeatherLocation`), the weather cache, the onboarding flags (`local`), the legacy favorites keys (`docs/remove-migrations.md` decision 2) and every other key stay as they are.
   The page's handler (`resetGrid`, started by the dialog's Reset grid button): `startFavoritesAction({ render: false })` (busy), `await resetUnreadableWidgets(syncStorageArea)`; **on any result (`reset: true` or `false`) the page reloads (`location.reload()`)**: the normal first load then runs (`ensureWidgetsLayout` for the first screen of the new window, the weather, the first-run decision), which is what "start a fresh install" means, and for `reset: false` it shows whatever is stored now. On a rejection: `finishFavoritesAction`, the dialog closes (focus to the screen's button, no scroll), `#desktop-status` shows **`Couldn't reset your grid. Try again in a moment.`** (the page-level failure place, as for the delete confirm; cleared by the next action or after 8 s, `DESKTOP_STATUS_MS`), and the screen stays; a second attempt is allowed at once.
   Ruling (марафон, на проверку Киру): the reset keeps the weather city and the onboarding flags, so a person who already onboarded gets the six default tiles with the stored city back, and a profile that never finished onboarding gets the first-run wizard as any fresh install does; альтернатива: erase the city and the flags too (a complete fresh install: no city, the wizard again); цена ошибки: a person who wanted a complete start has to change the city by hand (one dialog); erasing it silently would cost the city of a person who only wanted the links reset, and the confirmation names links only.
   No in-page re-render and no announcement: the page reloads, so the new page starts at its top with no focus, and the screen reader reads the new page; accepted (Accepted exception 4).

7. **Slow and failing storage.** The removal has no timer of its own. A removal that answers after more than the 8 s of the status chip, with success, must give the same result as a fast one: the dialog stays open and busy for the whole time, no chip text appears, then the page reloads (AS-UGR-10). A removal that rejects (AS-UGR-11) shows the chip text above after it rejected, not before. A removal that is slow and then rejects shows the chip when it rejects and keeps the screen.

8. **Other tabs and a stale screen (closes Accepted exception 10 of run 50).**
   - A tab that shows a healthy grid and sees the meta go bad in another tab is left alone by a return, as `docs/tab-return-refresh.md` decision 5 step 3 says (zero change, nothing written, no message). Its next write is refused with `INVALID_WIDGETS_MESSAGE`; its reload shows the screen. A return never replaces a grid the person is looking at by the screen.
   - A tab that shows the screen is a locked-like state (`widgetsState` is `null`): a return does not re-read it. The screen therefore stays until a reload or a press of Reset grid, even when another tab has reset or fixed the data meanwhile. Ruling (марафон, на проверку Киру): the screen is not refreshed by a return; the guard of decision 6 makes the stale button safe (it erases nothing that is readable, and reloads to show the real state); альтернатива: let the return re-read the meta and draw the grid when it became readable (the decision of `refreshDeskOnReturn` would have to treat the screen as drawn and the render would have to drop the flag), also replacing the screen by the grid without a press; цена ошибки: with the chosen rule a stale screen can offer a reset that does nothing and shows the real grid after one extra confirm; with the alternative `refreshDeskOnReturn`, which needed several spec rounds in run 50, grows a branch for a state that almost no real user can reach.
   - Two screens pressed at once: the lock serializes them; the second finds a readable meta and erases nothing (AS-UGR-12).

9. **Keyboard and names.** The screen's only tab stop is Reset grid; it is a native button (Enter and Space activate). The confirm dialog follows the focus rules of every desktop dialog (focus Cancel, Tab cycles Cancel and Reset grid, Escape closes). `p[role=alert]` is the one live announcement of the screen (as for `newer`); nothing is added to `#desktop-live`.

10. **Documents and notes** (`### Document texts` gives the words): `CHANGELOG.md` `[Unreleased]`; `docs/architecture.md` (bootstrap, the unreadable-meta paragraph, the modules table, the placement sentence); `agent-config/CLAUDE.md` (the store API line, Bootstrap R7, the desktop-dialog list, the `centeredDefaultRow` description); `docs/design-system.md` (the "Examples by screen" table gets `Reset grid?`); a one-line "Changed by run 51" under the Status of `docs/remove-migrations.md`, `docs/vertically-centered-defaults.md`, `docs/post-onboarding-grid.md`, `docs/tab-return-refresh.md`, only where their text claims what changed. `docs/privacy.md` and `store/` are unchanged: the button removes the extension's own keys from the local and synced storage and sends nothing.

## Review focus

- **Scenarios and states:** every way into the screen (early read, the second exit through `ensureWidgetsLayout`, a failed early read) and every way out (Cancel, Escape, backdrop, confirm, a slow removal, a failing removal, a stale screen, two screens at once) end in one of the stated states; `resetUnreadableWidgets` erases only under the lock and only for `invalid`; the 300 ms pointer guard against the double click is the one real hazard of the screen (Live measurement) and has a premise that proves it is a window; the cap changes only windows of 960 px and more and every path that calls `centeredDefaultRow` (the default block, the heal, the island); `sizeOf`'s new default for a metric agrees with `placeholderGrid`.
- **Visual and layout:** the centered block at 1280×800, 1280×200, 640×400, 500×800 and 320×600, light and dark; the button keeps its natural width below 601 px; the failure chip under and after the dialog (`body:has(.desktop-dialog)` hides it only while a dialog exists, so it appears after the close); nothing of the grid chrome is reused or moved.
- **Accessibility and texts:** `role=alert` text plus a native button; the dialog name, description and focus; no new live-region text; the product strings of `### Document texts`; contrast of the danger text in both themes; no keyboard trap on the screen.

## Accepted exceptions

1. **Item 44 stays as decided by Kier:** two fresh installs before Chrome Sync delivers the other's keys can write the six system keys to different rows, and a merge by key can tear the block apart. Not reproducible in the harness, hard to cure; with the ceiling the rows of two windows now differ only up to row 4, so the exposure is smaller than before. No work.
2. **Reset is cross-device.** The removal goes through Chrome Sync like every write, so the grid's keys disappear on the account's other devices too; they were unreadable here and can be readable only to an older build there. The confirmation names links only (Kier's words).
3. **The city and the first-run flags stay (Ruling in decision 6).** A person who expected a complete start finds the city set; a person who never finished onboarding on this profile meets the wizard.
4. **The reset reloads the page.** There is no in-page success state and no announcement: the new page starts with no focus and the screen reader reads it as a new page. A person who pressed Reset grid sees the page flash once.
5. **A stale screen stays stale** until a reload or a press (Ruling in decision 8); a return does not draw the screen over a healthy grid either (decision 8, closes Accepted exception 10 of run 50).
6. **The 300 ms pointer guard does not cover a slow deliberate second click.** After 300 ms the dialog is plainly visible and a click on its button is a decision.
7. **A window with fewer than 5 rows** (under 424 px at width 1280) shows a block stored at row 4 only by scrolling; a profile written in a window of 400 px keeps its own lower row; a block already stored at row 5 or lower by an earlier build stays there (no recomputation, no migration).
8. **A tall window shows the block above the middle** by the owner's decision (the cap), and the island too (Ruling in decision 2).
9. **Items that are unreadable one by one** (a valid meta whose item has bad fields) are left out of the read as before and stay in storage; no screen, no reset for them (Non-goals).
10. **A stored `tileSize` stays in a profile as ignored data**; an item that carried `tileSize: "huge"` and was invisible before is visible now.
11. **`INVALID_WIDGETS_MESSAGE` is not reworded** ("Reload this tab" is now true advice).
12. **A failure of the first read and of every later read** (storage down) is the existing `favoritesError` text, not the screen.

## Non-goals

- Resetting or erasing for a `newer` meta; any automatic reset; a backup, export or undo of the erased grid; a partial recovery of single items; repairing a meta.
- Erasing the city, the weather cache, the first-run flags, the legacy favorites keys or any key that is not `quietTabWidgetsMeta` or `quietTabWidget:<id>`.
- Re-reading the grid on a return for the unreadable cases, drawing the screen on a return, any change to `refreshDeskOnReturn`, `healClearedDesk`, `recoverFromGoneLink` (run 50 and runs 29 to 31 stay).
- Chrome Sync partial arrival and the item 44 cure; a per-height ceiling; recomputing a stored row; a migration of old rows; any change to `placeNew`, the self-heal row, the drag drop area, the weather tiles or the wizard.
- New storage keys or formats, new permissions, new requests, a new setting; changes to `docs/privacy.md` or `store/`.
- `clearState` (test-only) and the other dead exports of the store; the `tileSize` mentions of historical specs beyond the notes of decision 10.
