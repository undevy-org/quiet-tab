## Terms

- **Natural document height**: `documentElement.scrollHeight` with no hold. **`restingMax`** = natural height − `clientHeight` (the largest `scrollY` the page allows without a hold).
- **Hold** (`h` px, `h >= 0`): extra document height below the grid, added by this feature and nothing else. `restingMax` is always measured without it.
- **Settling**: from the end of a started drag (`onDragPointerUp` after the 6 px threshold, or `cancelDrag` with a started drag) until the drop is over: `commitDrop`'s promise has settled and, if `returnDraggedTile` runs, its `finish` render has happened; for the paths that render at once (drop on the own cell, `cancelDrag`) the settling is that one render.

## Triage (reading `main`)

- **Target recompute today.** `updateDragTarget(s)` reads the grid box (`getBoundingClientRect`, so it already follows the scrolled page) and the stored pointer position `s.lastX/lastY`, and judges `clampDropCell(cellFromPoint(point, box, metrics, s.grab), size, columns, s.maxY)` with `canPlace`. It is called from `applyDragVisuals` (pointer move) and from `autoscrollFrame` (only when the autoscroll moved the page). Any other scroll while a drag is active (wheel, trackpad, keyboard Page Down / Space / arrows, scrollbar drag, scroll anchoring) moves the grid under a still pointer and leaves the target stale.
- **Why the page gets shorter (item 19).** While dragging `.desktop-grid` is `--rows: s.rows = max(occupiedRows, maxY + h)` high. After the drop `renderFavorites` rebuilds the grid at its resting `--rows` (`max` of `y + h` of all tiles, from the displayed layout). The document after the drop is shorter than the document at the time of the drop whenever the drop frees the lowest rows (the dragged tile was alone in the bottom row(s), and the next occupied row is higher), or the drag grid was higher than rest (the tile was not alone in the bottom row, `maxDropRow` = lowest other row + 1). If `scrollY` is above the new `restingMax`, the browser clamps it at the next layout and everything below the old top moves down by the difference. The same render happens on EVERY end of a started drag: a successful drop (`runDesktopMutation` success), a drop on the own cell (`renderFavorites()` at once), `returnDraggedTile`'s `finish` after a rejected drop or a failed write (180 ms later, or at once with reduced motion) and `cancelDrag` (Escape, blur, pointer leaves the window, pointercancel, resize, leaving edit mode; at once). The clamp case is therefore all of them, not only a committed drop; it needs `scrollY > restingMax` of the document after the render.
- **Not a defect:** a drop with `scrollY <= restingMax` of the document after the render (in particular `scrollY` 0 and a page that fits): nothing is clamped (§ Controls).

## Decisions

1. **The target follows every scroll of the page during a drag, and a release judges the current page (item 18).** One passive `scroll` listener on `window` is registered once at boot, next to the other window-level drag listeners (`pointermove`, `pointerup`, `pointercancel`, `blur`), not attached and removed per drag. Its handler: if a started drag exists (`dragSession?.started`), call `updateDragTarget(dragSession)` synchronously, with the last pointer position `s.lastX/lastY` (the browser already delivers one `scroll` event per frame, so no extra coalescing); without a started drag, it only runs the lazy release of decision 2. In addition `onDragPointerUp` calls `updateDragTarget(s)` once, from `s.lastX/lastY` against the current grid box, immediately before it reads `desktopUi.drag`, so a release in the same frame as a scroll (the `scroll` event not yet dispatched) writes to the cell under the pointer, not to the old outline. The autoscroll frame keeps its own `updateDragTarget` call (a duplicate call in the same frame is idempotent). Requirement for every end path (drop, rejected drop, `cancelDrag`, `reattachDrag`'s drag-lost branch): after the drag ended, the `scroll` handler never creates, moves or redraws a `.drop-highlight` and never touches `[data-dragging]`. No new text, no new control, no change to the pointer rules.
2. **The tile lands where the outline was: the page keeps the height it needs (item 19).** At every render that ends a drag (decision 2a) the document gets a hold exactly as large as needed so that the browser does not clamp `scrollY`; the settled tile and every other tile stay exactly where they were on screen. Nothing a layout reads (`documentElement.clientHeight/Width`, `--rows`, `gridMetrics`, `viewportRows`) may change, and the stored layout, `maxDropRow` and the DOM contract stay as they are.
   - **2a. When it is set (at render time, every path).** The hold is computed and applied inside the render that follows a started drag, on all paths: the render after a successful write, after a drop on the own cell, `returnDraggedTile`'s `finish` render (rejected drop, failed write, `commitDrop` with `favoritesBusy`; with and without reduced motion), `cancelDrag`'s render (its call from the resize handler included), and `recoverFromGoneLink`'s render; and in every other render that happens during the settling (a weather render while the write is pending, with `pendingDrop` re-applied), so the hold exists in each frame in which the DOM is at resting height. Inside the settling the hold is the pure formula `h = pageHoldHeight(scrollY, clientHeight, naturalHeight) = max(0, ceil(scrollY + clientHeight − naturalHeight))` (`ceil`: `scrollY` and the heights can be fractional at a device pixel ratio or zoom; a hold short by a fraction of a pixel would never be released and would clamp by that fraction). If `h = 0` nothing is held: this is the case for `scrollY` 0, for any `scrollY <= restingMax` after the render, and for a page that fits (decision 3), so the rule has one condition and no mode. During the 180 ms return the DOM is still the drag-height grid (no render), so nothing is clamped; the finish render sets the hold; the result does not depend on `prefers-reduced-motion` (decision 4).
   - **Order inside `renderDesktop` (fixed).** (1) `scrollY` is read as the FIRST statement, before `applyGridMetrics()` (which writes the grid metrics and can force a layout) and before anything that lets a layout run; (2) the render builds and replaces the grid (`replaceChildren`) as today; (3) the hold is cleared (the custom property is on `.desktop`, which is not recreated, so it survives the render and must be reset explicitly); (4) `naturalHeight` = `documentElement.scrollHeight` is measured; (5) the new hold is set from (1) and (4); (6) only then, if the measurement clamped `scrollY`, `scrollTo(0, scrollY)` restores the value read in (1), in the same task, before any paint. The early exits of `renderDesktop` (`widgetsNewer`, no `widgetsState`: the error status replaces the grid) do not touch the hold and do not run (1) to (6).
   - **2b. How long it lasts (lazy release).** The hold is never released by an event that would make the browser clamp. Outside the settling it can only shrink: a render computes `h_new = min(pageHoldHeight(…), h_old)`, so a render that is not a drop's (a delete or a Hide at the bottom, which clamps as today, Non-goals; a weather render; leaving edit mode; a resize) never raises a hold that exists and never creates one. It is released: (i) in the `scroll` handler (no drag), when a hold exists and `scrollY + clientHeight <= naturalHeight + 1` (the +1 px absorbs fractional values; so `scrollY <= restingMax` within a pixel; the document shrinks to natural with nothing to clamp and no content moves); a handler call with no hold and no started drag reads nothing from the layout (no forced layout, no cost); (ii) by every later render through `h_new` above, which lowers or removes it when the new layout makes it unnecessary; (iii) leaving edit mode and a viewport resize are such renders: they recompute by `h_new`, they do not clear the hold by force (clearing would cause a clamp for nothing); if the new layout is lower than the old one, `scrollY` stays where it is and the content does not move, the hold lasts until (i). It is NOT released by a scroll that keeps `scrollY + clientHeight > naturalHeight + 1` (including a scroll up by 1 px to 80 px), by the next drag start, by a dialog opening or closing, by focus, by a `scroll` event caused by `focusDragTile` or by the reveal of `recoverFromGoneLink`, or by a weather render.
   - **Mechanics are the implementer's choice inside these rules.** Recommended: a px value on `.desktop` added to its bottom padding through a custom property (`padding-bottom: calc(var(--grid-pad) + var(--status-reserve, 0px) + var(--drag-hold, 0px))`); it is additive with the chip reserve of run 46 by construction (a `min-height` on the border box would not be: a chip appearing later would be absorbed in it), `naturalHeight` is `scrollHeight − hold`, and no layout input changes. The pure arithmetic (`h` from `scrollY`, `clientHeight`, `naturalHeight` with `ceil`; `h_new = min(h, h_old)` outside the settling; the release condition with the +1 px) is extracted as a helper in `desktopLayout.js` and unit-tested, including fractional values.
   - **Next drag while a hold exists:** the hold stays (drag start does not release it). The new drag grid is taller or equal; the document is only higher than needed; nothing moves under the pointer (`baseTop` is taken from the rect at `pointerdown`). The next drag's end recomputes the hold by 2a.
3. **A page that fits, and a drop that cannot clamp, are untouched.** `h = 0` whenever `scrollY + clientHeight <= naturalHeight` after the render: a page that fits (document height ≤ window height), `scrollY` 0, and any `scrollY <= restingMax` (a drop at `scrollY` 300 on the 188-link desk). Nothing is held and nothing differs from today.
4. **Reduced motion.** No animation is added; the hold is a layout fact computed at render time, identical with and without `prefers-reduced-motion` (the return animation only decides when `finish` renders; it never holds anything itself).

Ruling 1 (item 19). Ruling (марафон, на проверку Киру): after a drag ends on a scrolled page, the page keeps exactly the height that its current `scrollY` needs (the hold) until the user scrolls up out of it, so the tile never jumps and no later event (leaving edit mode, a resize, a dialog, a new drag) moves the page either; альтернатива: let the browser clamp `scrollY` and accept the jump (80 px at 1280×800; 72 / 62 px at 500×800 / 320×600) or animate it, or compensate `scrollY` (impossible: the document is shorter than `scrollY` + window, so the clamp happens first); цена ошибки: while the hold lasts, an empty band of `h` px sits under the last tile in edit mode, visible only when the user scrolls to the bottom. `h` is the height the drop freed at the bottom of the grid, plus the drag grid's extra rows when it was higher than rest: the gap between the dropped tile's old row and the next occupied row above it (one row, `cell + gap`, for a tile one row below its neighbour; `k` rows when the nearest occupied row is `k` rows higher), never more than that gap and never more than the document held before the drop. It disappears when the user scrolls up to `scrollY <= restingMax` (typically one scroll step: 20–80 px at the bottom); no release moves the content, because it happens only where nothing can clamp.

## Review focus

- **Scenarios/states:** the `scroll` handler is a single window listener that never acts on a drag that has ended (drop, rejected drop, own-cell drop, Escape, blur, pointer leave, pointercancel, resize, edit mode exit, `reattachDrag` losing the tile); a scroll that arrives after `onDragPointerUp` must not touch a finished drag; a release in the same frame as a scroll writes to the cell under the pointer. The hold is set at render time on EVERY path that ends a started drag (success, own cell, `finish`, `cancelDrag`, `recoverFromGoneLink`, a render mid-write) and is released only lazily (no event that causes a clamp); never stuck (after a failed write, after a weather render, after a second drag, after `LinkGoneError`).
- **Visual/layout:** tile and outline rectangles agree within 1 px after a drop at every width, on every sampled frame; no frame in which another tile moves; the added band is exactly the shortage, disappears when the user scrolls up out of it; the hold does not change `clientHeight`/`viewportRows`; the chip reserve of run 46 (`--status-reserve`, `.desktop` padding-bottom) stays additive and exact.
- **Accessibility/texts:** no new text; focus returns to the dropped tile; reduced motion does not change the result; screen-reader order of the tiles is untouched.

## Accepted exceptions

1. While the hold lasts, the empty band under the last tile in edit mode (and after leaving it) is `h` px high (the freed rows, Ruling 1; cost of the alternative being a jump of the dropped tile); it ends when the user scrolls up to `restingMax`. There is no jump at any release: leaving edit mode and a resize recompute the hold and never clear it by force (revision 3; revision 2 accepted one clamp there).
2. A scroll caused by the browser's own scroll anchoring, by `scroll-margin` focus alignment during a drag, or by `focusDragTile` right after a drop or a return (up to 6 px when the tile is within 6 px of a window edge, AS-DST-04 (iv), AS-DST-07) moves the outline (during a drag: the target always follows the pointer, not the tile's origin) or nudges the page once; after a drop it never releases the hold by itself (decision 2b), so no clamp follows it.

## Non-goals

- Changing the autoscroll speed, edge size (48 px) or step (12 px); adding wheel acceleration or inertia handling.
- Changing the drop rules (`maxDropRow`, `clampDropCell`, `canPlace`), the drag threshold, the whole-window drop area (`docs/widget-drag-limits.md`), or the drag grid height.
- Holding or compensating scroll for any render other than the ones that end a started drag (a delete or a Hide at the bottom of a scrolled page clamps as today; with a hold alive the hold never grows because of it, decision 2b).
- Touch dragging, keyboard-only tile moving, the status chip geometry (run 46), the Add menu position, weather reliability (Р48), typography (Р49).
- Any storage change, new text or control.
