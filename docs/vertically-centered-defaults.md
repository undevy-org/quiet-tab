Horizontally the block is already centered (`docs/centered-grid.md`). Center the same default block **vertically in the first screen**, at the **very first** appearance of the grid after install. ## Current behaviour (`main` at `4ca70eb`)

Fresh install at 1280×800 (14 columns, cell 72, gap 8, pad 16): the bootstrap runs the migrations, then `ensureWidgetsLayout` (`src/newtab.js:2245`), which finds all six system items absent and calls `placeMissing(absent, existing)` (`src/widgetsStore.js:710`). `placeMissing` builds one 8-wide row block and takes the first row (from 0) with a free 8-run, nearest to the center of the 12 reference columns, so the stored grids are temperature (−4,0), precipitation (−3,0), air quality (−1,0), UV (1,0), Settings (2,0), Add (3,0). The tiles are drawn at displayed columns 3..10, row 0: top edge 16 px, bottom 88 px, in a window 800 px high that holds `viewportRows(800, 1280) = 9` rows (`src/desktopLayout.js:39-42`). The block center is at 52 px, the window center at 400 px.

On a first run with no city the first-run modal opens before the first render (`docs/first-run-empty-desk.md`): `ensureWidgetsLayout` has already written the six items, the desk (`#favorites`) is veiled (`visibility: hidden`) while the modal is open, and the tiles appear in place when the modal closes (Not now, Escape, backdrop, or a successful Save). The stored `y` never depends on the window again: `displayLayout` draws a stored cell as stored (`src/desktopLayout.js:126-150`), a resize writes nothing, and every later write re-bases `x` only for the column count (`docs/centered-grid.md` decision 2).

`viewportRows` (`src/desktopLayout.js:39-42`) is already the product's definition of "the first screen": the drag code uses `viewportRows(document.documentElement.clientHeight, viewportWidth())` (`src/newtab.js:1895`) so that every row of the first screen is a drop target (`docs/widget-drag-limits.md`, `maxDropRow`).

The status line `#desktop-status` (`src/newtab.html:15`, `src/newtab.css:185-201`) is `position: fixed; bottom: var(--status-chip-offset-bottom)` (16 px), centered, `hidden` unless a message is set. It is **not in the flow** and does not take rows from the first screen: `viewportRows` does not subtract it, the grid is laid out the same with or without it. At boot it is empty except for the persistent ensure-failure message (`ENSURE_FAILED_MESSAGE`, `src/newtab.js:61`), which only exists when the write of the defaults failed, i.e. when there is no default block to place.

## Default decisions (owner can override)

1. **Only the first placement of the whole block.** The new rule applies when `placeMissing` is asked for **all six** default ids (`ensureWidgetsLayout`: `absent` has six entries: every system item is missing or unreadable). It does not apply when 1 to 5 ids are missing (self-heal, the legacy upgrade where the metrics come after the links): that path is the code of run 15 byte for byte (first row from 0 that has a free run, nearest to the center, `docs/centered-grid.md` decision 6). So a fresh install, or storage cleared completely, centers; everything else behaves as today. *Rejected:* centering the self-heal too (owner: stays as it is); remembering "this is the first appearance" in storage (no new field: "all six absent" is exactly the state of the first appearance, and no user can be in it twice without clearing the data).
2. **The first screen = `viewportRows(clientHeight, clientWidth)`, sampled once at boot.** `R = viewportRows(document.documentElement.clientHeight, viewportWidth())`, the same call and the same two inputs as the drag (`src/newtab.js:1895`): the number of whole rows between the top padding and the bottom padding (`floor((H − 2·pad + gap) / (cell + gap))`, at least 1; cell, gap and pad from `gridMetrics(clientWidth)`). One definition of "first screen" for drop targets and for the default block. It is read in `newtab.js` immediately before `ensureWidgetsLayout` (after the migrations, before `getState()` and before the first render) and passed in as `screen: { rows: R, columns: C }` with `C = currentColumns()` (`src/newtab.js:1735`). *Availability checked in the code:* `newtab.js` is a `type="module"` script at the end of `<body>` (`src/newtab.html:16`), so it runs after the document is parsed; `document.documentElement.clientHeight` is the viewport height (it does not depend on the content, the grid or the stylesheets, and needs no render), it is read by the same code at the same stage for the width (`currentColumns()` before the first render) and is used for the drag at any time. The veil (`height: 100vh; overflow: hidden` on `#favorites` only) does not change it. A value that is not a finite number (for example 0 in a window that is not laid out yet) gives `viewportRows = 1` (the function's own minimum), which means row 0, exactly as today. *Rejected:* the height of `.desktop-grid` (it is 0 before the first render and is derived from the rows the tiles use, so it cannot say where the tiles should go); the pixel center `H/2` (flips rows at pixel thresholds that differ from the drag's first screen, and depends on the leftover pixels below the last row).
3. **The height of the block is the DISPLAYED height.** All six tiles are stored in one row `Y`, but the page draws them with `displayLayout` at the page's column count `C`: one row when `C ≥ 8` (the block is 8 cells wide, e.g. 600 px or 664 px and wider), two rows when `C` is 4 or 6 (the same wrap as AS-CG-07: at 500 px row 0 holds temperature, precipitation, air quality, UV and row 1 Settings and Add; at 320 px air quality drops to row 1), and four rows at `C = 2` (a window narrower than anything Chrome allows; the code takes the number from the engine, not from a table). `blockRows = defaultBlockRows(C)` is computed by `displayLayout` over the six default items at `y = 0`, so the rule follows the engine if the wrap ever changes. *Why:* 500 and 320 px are required cases and the rectangle that must be centered is the one the user sees. *Rejected:* centering the stored one-row block only (a two-row rectangle would hang half a row too low on narrow windows).
4. **The row.** `Y0 = max(0, floor((R − blockRows) / 2))`. For a one-row block (`C ≥ 8`): `floor((R − 1) / 2)`. Odd `R − blockRows`: the block is exactly in the middle of the rows of the first screen. Even `R − blockRows` (an even number of free rows): the free rows split unevenly by one and the **extra free row goes below** (the block sits one row above the geometric middle). Reasons: (a) the rule is the same integer arithmetic as the drag's first screen and never reads pixels, so the same window height gives the same row everywhere; (b) the bottom part of the window carries more visual weight (the leftover pixels under the last whole row, the fixed status line), so the optical middle of a page is slightly above the geometric one; (c) the block is never lower than the middle of the window, so it is never pushed toward the bottom edge or the status line; (d) `max(0, …)` keeps the block off the area above row 0 when it is taller than the first screen (a low window): the block then starts at row 0 and may extend below the fold like any tall layout. Examples at width 1280 (one-row block, cell 72, gap 8, pad 16, step 80): H 800 → `R = 9`, `Y0 = 4`; H 700 → 8, 3; H 600 → 7, 3; H 500 → 5, 2; H 400 → 4, 1; H 300 → 3, 1; H 200 → 2, 0; H 150 → 1, 0; H 100 → 1 (the function's minimum), 0; H 1080 → 13, 6; H 1440 → 17, 8; H 2160 → 26, 12. Two-row block: 500×800 (cell 64, gap 8, pad 12, step 72) → `R = 10`, `Y0 = 4` (rows 4 and 5); 601×800 → `R = 9`, `Y0 = 3` (rows 3 and 4); 320×600 (cell 56, gap 6, pad 8, step 62) → `R = 9`, `Y0 = 3` (rows 3 and 4). Measured, the block's vertical center is at the middle of the first screen's rows (`pad + (R·cell + (R−1)·gap) / 2`) when `R − blockRows` is even and half a step above it when it is odd; it is never below the window's center (`H/2 − center` is in `[0, step)`).
5. **If the target row is not free.** `placeMissing` already knows the other items (`existing`, on the grid, with a valid grid, mapped to the 12 reference columns as today). The block needs a free 8-run in the row. Rows are tried by distance from `Y0`: `Y0`, `Y0 − 1`, `Y0 + 1`, `Y0 − 2`, `Y0 + 2`, … (a row below 0 is skipped; the nearer row **above** wins a tie, the same bias as decision 4), and the first row that has a free run takes the block, at the position nearest to the reference center, ties to the right (the run 15 rule, unchanged). The search is unbounded downward, so it always ends. It does not fall back to row 0 and does not stay inside the first screen: the nearest free row is the one closest to the middle, wherever it is. When nothing is on the grid (the normal first appearance) the row is `Y0`. A 2-high item occupies the row below too, as today.
6. **Measured once, never recomputed.** The stored `y` is whatever it was at the moment of the first write. A later resize, a reload, a different window size, another tab, the first-run modal opening or closing, drag, edit mode: none of them recompute or rewrite `y` (every later write stores the displayed grids as it does today). Consequences accepted below: a window resized between the write and the reveal, and a profile later opened in a much lower window, show the block where it was put. Two tabs opened at once: both run `ensureWidgetsLayout` under the extension-wide mutation lock; the first writes with its own window size, the second finds the items and writes nothing.
7. **A partial self-heal is unchanged, including where the tile goes.** With the block at row `Y0 > 0`, a missing single tile (for example Add) is put back by the run 15 rule: the first row from 0 that has a free cell, nearest to the center, which is **row 0**, not next to its siblings. Owner decision: the self-heal stays as it is. It is a rare path (the system items are not deletable from the UI); see Accepted exceptions.
8. **Where it lives.** Pure engine: `placeMissing(missingIds, existing, screen)`; `screen` is optional and means `{ rows, columns }`; without a valid `screen` (both integers, `rows ≥ 1`, `columns ≥ 2`) the target row is 0 and the result is today's. New pure helpers in `src/desktopLayout.js`: `defaultBlockRows(columns)` and `centeredDefaultRow(rows, blockRows)` (decision 4) and the row search of decision 5. `ensureWidgetsLayout(storageArea, { now, screen })` passes `screen` through to `placeMissing`; the only production caller, `newtab.js`, supplies it (decision 2). `widgetsService.js` does not call either function and does not change.
9. **Nothing else changes.** No new text, control, colour, token, setting or storage field. The first-run modal, the veil and the reveal (run 14), the hint tile, drag, resize rules, `placeNew`, the horizontal centering, the even columns and the signed `x` stay as they are. **Data compatibility: not required** (no storage format change: the same six items with the same shapes; only the value of `y` of a first write differs).

## Non-goals

- Horizontal centering, the even column count, the signed `x`, `placeNew`, drag over the whole window (run 13), the repack of `displayLayout`, the resize rules, adding links, the self-heal of a single missing tile (all unchanged).
- Recentering on a window resize, on a reload or when the profile is opened on a window of another height (the stored `y` is never recomputed).
- Centering the first-run city window or changing the veil and the reveal (run 14).
- Any new control, text, setting or token; any storage field; any migration of earlier data (**Data compatibility: not required**).
- Reserving rows for the status line, or moving it (it stays a fixed overlay).

## Accepted exceptions

- **A window that changed between the write and the first look keeps the first measurement.** The block is placed from the window of the first boot. If the user resizes while the first-run modal is open (the desk is veiled), or opens the same profile later in a much lower window (for example 1280×300 after 1280×800: row 4 is below the 3 rows of that window), the block stays at the stored row and may need a scroll. Owner rule: the saved `y` is never recomputed.
- **Even number of free rows: the block is one row above the middle** (decision 4). At H 700 the block center is 292 px against a window center of 350 px (58 px above); at H 800 it is 372 px against 400 px (28 px above).
- **Narrow windows center a two-row rectangle that the page wraps from the left** (decision 3): the block is centered at the column count of the first boot. Widening the window afterwards makes it one row, so it then sits half a row lower than the middle; accepted (no recomputation).
- **A window shorter than the block** (`R < blockRows`: only the two-row block of a narrow window with `R = 1`, e.g. 500 px wide and under about 160 px high): the block starts at row 0 and its second row is below the fold. In very low windows (one row, about 104 to 183 px at 1280) the transient status line (fixed, bottom) may cover the block while a message is shown; that is the existing overlay behaviour at any height and is not designed here.
- **A restored single tile goes to row 0**, not next to the centered block (decision 7), because the self-heal rule is unchanged by the owner's decision.
- **The first tab decides when two tabs open at once** (decision 6): the other tab's window height is ignored.
- **A non-free target row can put the block outside the first screen** (decision 5): the nearest free row is used even when it is below the fold (only possible when other items already fill the middle rows, i.e. never on a real first appearance).

## Acceptance scenarios
