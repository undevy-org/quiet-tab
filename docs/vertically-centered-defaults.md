# Vertically centered defaults: the first block of tiles sits in the middle of the first screen

## Status

`draft`

Horizontally the block is already centered (`docs/centered-grid.md`). Center the same default block **vertically in the first screen**, at the **very first** appearance of the grid after install. ## Current behaviour (`main` at `4ca70eb`)

Fresh install at 1280×800 (14 columns, cell 72, gap 8, pad 16): the bootstrap runs the migrations, then `ensureWidgetsLayout` (`src/newtab.js:2245`), which finds all six system items absent and calls `placeMissing(absent, existing)` (`src/widgetsStore.js:710`). `placeMissing` builds one 8-wide row block and takes the first row (from 0) with a free 8-run, nearest to the center of the 12 reference columns, so the stored grids are temperature (−4,0), precipitation (−3,0), air quality (−1,0), UV (1,0), Settings (2,0), Add (3,0). The tiles are drawn at displayed columns 3..10, row 0: top edge 16 px, bottom 88 px, in a window 800 px high that holds `viewportRows(800, 1280) = 9` rows (`src/desktopLayout.js:39-42`). The block center is at 52 px, the window center at 400 px.

On a first run with no city the first-run modal opens before the first render (`docs/first-run-empty-desk.md`): `ensureWidgetsLayout` has already written the six items, the desk (`#favorites`) is veiled (`visibility: hidden`) while the modal is open, and the tiles appear in place when the modal closes (Not now, Escape, backdrop, or a successful Save). The stored `y` never depends on the window again: `displayLayout` draws a stored cell as stored (`src/desktopLayout.js:126-150`), a resize writes nothing, and every later write re-bases `x` only for the column count (`docs/centered-grid.md` decision 2).

`viewportRows` (`src/desktopLayout.js:39-42`) is already the product's definition of "the first screen": the drag code uses `viewportRows(document.documentElement.clientHeight, viewportWidth())` (`src/newtab.js:1895`) so that every row of the first screen is a drop target (`docs/widget-drag-limits.md`, `maxDropRow`).

The status line `#desktop-status` (`src/newtab.html:15`, `src/newtab.css:185-201`) is `position: fixed; bottom: var(--status-chip-offset-bottom)` (16 px), centered, `hidden` unless a message is set. It is **not in the flow** and does not take rows from the first screen: `viewportRows` does not subtract it, the grid is laid out the same with or without it. At boot it is empty except for the persistent ensure-failure message (`ENSURE_FAILED_MESSAGE`, `src/newtab.js:61`), which only exists when the write of the defaults failed, i.e. when there is no default block to place.

## Default decisions (owner can override)

1. **Only the first placement of the whole block.** The new rule applies when `placeMissing` is asked for **all six** default ids (`ensureWidgetsLayout`: `absent` has six entries: every system item is missing or unreadable). It does not apply when 1 to 5 ids are missing (self-heal): that path is the code of run 15 byte for byte (first row from 0 that has a free run, nearest to the center, `docs/centered-grid.md` decision 6). So a fresh install, or storage cleared completely, centers; everything else behaves as today. *Rejected:* centering the self-heal too (owner: stays as it is); remembering "this is the first appearance" in storage (no new field: "all six absent" is exactly the state of the first appearance, and no user can be in it twice without clearing the data).
2. **The first screen = `viewportRows(clientHeight, clientWidth)`, sampled once at boot.** `R = viewportRows(document.documentElement.clientHeight, viewportWidth())`, the same call and the same two inputs as the drag (`src/newtab.js:1895`): the number of whole rows between the top padding and the bottom padding (`floor((H − 2·pad + gap) / (cell + gap))`, at least 1; cell, gap and pad from `gridMetrics(clientWidth)`). One definition of "first screen" for drop targets and for the default block. It is read in `newtab.js` immediately before `ensureWidgetsLayout` (after the migrations, before `getState()` and before the first render) and passed in as `screen: { rows: R, columns: C }` with `C = currentColumns()` (`src/newtab.js:1735`). *Availability checked in the code:* `newtab.js` is a `type="module"` script at the end of `<body>` (`src/newtab.html:16`), so it runs after the document is parsed; `document.documentElement.clientHeight` is the viewport height (it does not depend on the content, the grid or the stylesheets, and needs no render), it is read by the same code at the same stage for the width (`currentColumns()` before the first render) and is used for the drag at any time. The veil (`height: 100vh; overflow: hidden` on `#favorites` only) does not change it. `clientHeight` is an integer, 0 or more. 0 (a window that is not laid out yet) and any negative number give `viewportRows = 1` (the function's own minimum: a valid screen with one row, `Y0 = 0`, row 0 exactly as today; see Accepted exceptions). A value that is not a number (`NaN` or `undefined`, only in a broken environment) gives `NaN` and `Infinity` gives `Infinity` (`Math.max(1, NaN)` is `NaN`): `screen.rows` is then not an integer, decision 8 rejects the whole `screen`, and the target is row 0, again as today. Either way the first placement never fails and never leaves row 0 on a bad measurement (AS-VC-13). *Rejected:* the height of `.desktop-grid` (it is 0 before the first render and is derived from the rows the tiles use, so it cannot say where the tiles should go); the pixel center `H/2` (flips rows at pixel thresholds that differ from the drag's first screen, and depends on the leftover pixels below the last row).
3. **The height of the block is the DISPLAYED height.** All six tiles are stored in one row `Y`, but the page draws them with `displayLayout` at the page's column count `C`: one row when `C ≥ 8` (the block is 8 cells wide, e.g. 600 px or 664 px and wider), two rows when `C` is 4 or 6 (the same wrap as AS-CG-07: at 500 px row 0 holds temperature, precipitation, air quality, UV and row 1 Settings and Add; at 320 px air quality drops to row 1), and four rows at `C = 2` (a window narrower than anything Chrome allows; the code takes the number from the engine, not from a table). `blockRows = defaultBlockRows(C)` is computed by `displayLayout` over the six default items at `y = 0`, so the rule follows the engine if the wrap ever changes. *Why:* 500 and 320 px are required cases and the rectangle that must be centered is the one the user sees. *Rejected:* centering the stored one-row block only (a two-row rectangle would hang half a row too low on narrow windows).
4. **The row.** `Y0 = max(0, floor((R − blockRows) / 2))`. Let `F = R − blockRows` be the number of free rows of the first screen. For a one-row block (`C ≥ 8`): `Y0 = floor((R − 1) / 2)` and `F = R − 1`.
   - `F` even: the free rows split equally and the block is exactly in the middle of the rows of the first screen.
   - `F` odd: the free rows split unevenly by one and the **extra free row goes below**: the block sits half a step above the middle of the rows (40 px at step 80, i.e. a window wider than 600 px; 36 px at step 72, 361 to 600 px; 31 px at step 62, up to 360 px). For a one-row block `F` is odd exactly when `R` is even: this is the "even number of rows" case of the owner's note.
   - Reasons for `floor` (the extra row below): (a) the rule is the same integer arithmetic as the drag's first screen and never reads pixels, so the same window height gives the same row everywhere; (b) the bottom part of the window carries more visual weight (the leftover pixels under the last whole row, the fixed status line), so the optical middle of a page is slightly above the geometric one; (c) for `H ≥ 104` (a window with at least one whole row) the block is never lower than the middle of the window, so it is not pushed toward the bottom edge or the fixed status line; (d) `max(0, …)` keeps the block off the area above row 0 when it is taller than the first screen (a low window): the block then starts at row 0 and may extend below the fold like any tall layout.
   - Examples at width 1280 (one-row block, cell 72, gap 8, pad 16, step 80), with `R` and `Y0`: H 800 → 9, 4 (`F` = 8, even: exactly in the middle of the rows); H 700 → 8, 3 (`F` = 7: 40 px above the middle of the rows); H 600 → 7, 3; H 500 → 5, 2; H 400 → 4, 1 (40 px above); H 300 → 3, 1; H 200 → 2, 0 (40 px above); H 150 → 1, 0; H 100 → 1 (the function's minimum), 0; H 1080 → 13, 6; H 1440 → 17, 8; H 2160 → 26, 12 (40 px above). Two-row block: 500×800 (cell 64, gap 8, pad 12, step 72) → `R = 10`, `Y0 = 4` (rows 4 and 5); 601×800 → `R = 9`, `Y0 = 3` (rows 3 and 4); 320×600 (cell 56, gap 6, pad 8, step 62) → `R = 9`, `Y0 = 3` (rows 3 and 4; `F` = 7, odd, 31 px above the middle of the rows).
   - Measured: the block's vertical center is at the middle of the rows of the first screen (`pad + (R·cell + (R−1)·gap) / 2`) when `F` is even and half a step above it when `F` is odd. The distance to the **window** center also holds the leftover pixels under the last whole row (up to one step), so it is not the rounding: at 1280 it is 28, 58, 8, 38, 68, 18 px at H 800, 700, 600, 500, 400, 300 (AS-VC-01) and is in `[0, step)` for `H ≥ 104`.
5. **If the target row is not free (not reachable on a real first appearance).** At the real first appearance nothing else is on the grid (`existing` is empty), the row is `Y0`, and this decision never fires; it is defined because `placeMissing` is a pure function that can be given other items (all six absent while links are stored: only a hand-edited or partly cleared storage). Then the rule is: `placeMissing` knows the other items (`existing`, on the grid, with a valid grid, mapped to the 12 reference columns as today); the block needs a free 8-run in **one reference row**. Rows are tried by distance from `Y0`: `Y0`, `Y0 − 1`, `Y0 + 1`, `Y0 − 2`, `Y0 + 2`, … (a row below 0 is skipped; the nearer row **above** wins a tie, the same bias as decision 4), and the first row that has a free run takes the block, at the position nearest to the reference center, ties to the right (the run 15 rule, unchanged). The search is unbounded downward, so it always ends. It does not fall back to row 0 and does not stay inside the first screen: the nearest free row is the one closest to the middle, wherever it is. A 2-high item occupies the row below too, as today. *What it does not check (read in the code):* only the stored row `Y` is looked at (the 12-column reference frame, `blockRows = 1`). On a narrow window (`blockRows = 2`) the page draws the second part of the block in row `Y + 1`; `placeMissing` does not look at the occupancy of that displayed row. The display layout then lets the block win (it places items by stored `y`, then `x`, so the block takes its cells first) and other tiles stored in row `Y + 1` slide to the next free cell by the usual `displayLayout` rule; nothing overlaps and nothing is lost. AS-VC-10 covers 1280 only (one-row block); the narrow-window case is a state the product cannot produce (Accepted exceptions).
6. **Measured once, never recomputed.** The stored `y` is whatever it was at the moment of the first write. A later resize, a reload, a different window size, another tab, the first-run modal opening or closing, drag, edit mode: none of them recompute or rewrite `y` (every later write stores the displayed grids as it does today). Consequences accepted below: a window resized between the write and the reveal, and a profile later opened in a much lower window, show the block where it was put. Two tabs opened at once: both run `ensureWidgetsLayout` under the extension-wide mutation lock; the first writes with its own window size, the second finds the items and writes nothing.
7. **A partial self-heal is unchanged, including where the tile goes.** With the block at row `Y0 > 0`, a missing single tile (for example Add) is put back by the run 15 rule: the first row from 0 that has a free cell, nearest to the center, which is **row 0**, not next to its siblings. Owner decision: the self-heal stays as it is. It is a rare path (the system items are not deletable from the UI); see Accepted exceptions. `placeNew` has the same consequence for a new link and a restored metric (decision 9).
8. **Where it lives.** Pure engine: `placeMissing(missingIds, existing, screen)`; `screen` is optional and means `{ rows, columns }`; without a valid `screen` (both integers, `rows ≥ 1`, `columns ≥ 2`) the target row is 0 and the result is today's. New pure helpers in `src/desktopLayout.js`: `defaultBlockRows(columns)` and `centeredDefaultRow(rows, blockRows)` (decision 4) and the row search of decision 5. `ensureWidgetsLayout(storageArea, { now, screen })` passes `screen` through to `placeMissing`; the only production caller, `newtab.js`, supplies it (decision 2). `widgetsService.js` does not call either function and does not change.
9. **Nothing else changes.** No new text, control, colour, token, setting or storage field. The first-run modal, the veil and the reveal (run 14), the hint tile, drag, resize rules, `placeNew` (a new link or a restored metric still takes the first row from 0 with a free cell nearest to the center, which is **row 0, above** a block at `Y0 > 0`; Accepted exceptions, owner confirm), the horizontal centering, the even columns and the signed `x` stay as they are. **Data compatibility: not required** (no storage format change: the same six items with the same shapes; only the value of `y` of a first write differs).

- Moving the status line (it stays a fixed overlay that takes no rows; whether to reserve rows for it is an owner question, Review focus).

## Accepted exceptions

- **A window that changed between the write and the first look keeps the first measurement.** The block is placed from the window of the first boot. If the user resizes while the first-run modal is open (the desk is veiled), or opens the same profile later in a much lower window (for example 1280×300 after 1280×800: row 4 is below the 3 rows of that window), the block stays at the stored row and may need a scroll. Owner rule: the saved `y` is never recomputed.
- **Odd number of free rows (`F` odd, an even number of rows for a one-row block): the block is half a step above the middle of the rows** (decision 4). At H 700 (`R` = 8) the block center is 292 px against 332 px, the middle of the rows (40 px above), and 58 px above the window center (350 px); at H 800 (`R` = 9, `F` even) it is exactly in the middle of the rows (372 px) and 28 px above the window center, which is the leftover pixels under the last row, not the rounding.
- **Narrow windows center a two-row rectangle that the page wraps from the left** (decision 3): the block is centered at the column count of the first boot. Widening the window afterwards makes it one row, so it then sits half a row lower than the middle; accepted (no recomputation).
- **A window shorter than the block** (`R < blockRows`: only the two-row block of a narrow window with `R = 1`, e.g. 500 px wide and under about 160 px high): the block starts at row 0 and its second row is below the fold. Page scroll in such a window is the existing one: `.desktop` has a 16 px padding all around, so a window of 100 to 103 px high scrolls by 4 px (`scrollHeight` 104) at any block row 0; from 104 px up it does not.
- **The status line is an overlay and can cover the block in a very low window** (owner confirm, see Intake log). For a one-line message the chip is about 42 px high (2 × 10 padding, 2 × 1 border, 14 × 1.4 line) and its top is at `H − 58` px; the block in row 0 ends at 88 px, so they overlap when `H` is under about 146 px: in the one-row windows from 104 to 145 px (below 104 there is no real window; at 100 px the chip covers the block almost entirely). From 146 px up (and at every window with two or more rows) the chip is below the block. A longer, wrapped message is taller and reaches higher. This is the existing overlay behaviour at any height and is not designed here.
- **A zero-height window at boot keeps row 0 for good.** If the first measurement is made before the window is laid out (`clientHeight` 0 or negative), `viewportRows` gives 1 and `Y0 = 0`: the block is stored at row 0 and is not recentered later (decision 6), exactly as today.
- **A new link and a restored metric go to row 0, above the block** (owner confirm). `placeNew` is unchanged (decision 9): with the block at `Y0 > 0` the first row from 0 that has a free cell is row 0, so a link added through Add, or a metric put back, is drawn in row 0, centered, **above** the block, not next to it; at 1280×800 its top (16 px) is 320 px above the block's top (336 px). It then stays there like any other tile.
- **Another tile in the second displayed row of a narrow block** (decision 5): not checked by `placeMissing`; the display layout resolves it. Not producible on a real first appearance.
- **A restored single tile goes to row 0**, not next to the centered block (decision 7), because the self-heal rule is unchanged by the owner's decision.
- **The first tab decides when two tabs open at once** (decision 6): the other tab's window height is ignored.
- **A non-free target row can put the block outside the first screen** (decision 5): the nearest free row is used even when it is below the fold (only possible when other items already fill the middle rows, i.e. never on a real first appearance).

## Acceptance scenarios

Common setup unless stated: unpacked extension in the E2E harness (`--hide-scrollbars`, so `clientWidth` = window width); **fresh install** = an empty profile (`freshProfile`) opened, or `clearAll` then reload, at the stated window size, no city (the hint tile stands in the temperature cell, the other metric cells are reserved and have no tiles), the first-run modal not shown (the harness default) unless a scenario says "first run"; "stored" = `grid` in `chrome.storage.sync`; `Y0` as in decision 4; the six stored `x` are −4, −3, −1, 1, 2, 3 and `w`/`h` as the defaults, always; "the block" = the bounding rectangle of the drawn default tiles (the hint tile counts as the temperature tile); all measurements are `getBoundingClientRect` in client px with a tolerance of ±1 px; "block center" = (top + bottom) / 2; "rows center" = `pad + (R·cell + (R−1)·gap) / 2` for the window's `R`. "Nothing written" means `chrome.storage.sync` is deep-equal before and after, and no `chrome.storage.sync.set` call was recorded (`recordSyncSets`). At 1280 width: cell 72, gap 8, pad 16, step 80, so a block in row `Y` has top `16 + 80·Y` and bottom `88 + 80·Y`.

### AS-VC-01 A fresh install puts the block in the middle rows of the first screen
- Given: fresh install, width 1280, heights 800, 700, 600, 500, 400, 300 (`R` = 9, 8, 7, 5, 4, 3; odd and even).
- When: the page opens (first load of the profile) and the tiles are drawn.
- Then: stored `y` of all six is `Y0` = 4, 3, 3, 2, 1, 1 (and `x` −4, −3, −1, 1, 2, 3); all six tiles are in one row at displayed columns 3..10; block top = `16 + 80·Y0` = 336, 256, 256, 176, 96, 96 px and bottom = top + 72; block center equals rows center exactly (372, 292, 212, 132 for the odd `R` at 800, 600, 500, 300) or is 40 px above it (292 vs 332 at 700, 132 vs 172 at 400); `windowCenter − blockCenter` is in `[0, 80)` at every height (28, 58, 8, 38, 68, 18 px); the block is fully inside the window (bottom ≤ `clientHeight`); `scrollHeight === clientHeight` (no vertical scroll); storage holds exactly 7 keys (meta and six items, meta `version: 3`) written by two `set` calls (items, then meta), no other change from today.
- Verified by: E2E `dg-59` (group 1); `test/desktopLayout.test.js` (`centeredDefaultRow`, `placeMissing` with a screen); `test/desktopV2.test.js`.

## Review focus

- **Scenarios and states:** the "all six absent" condition (decision 1) and the paths that must stay as today (partial self-heal, a failing write); the single measurement at boot and what it means after a resize or a different window (decision 6, AS-VC-07, 08); the collision search (decision 5, not reachable on a real first appearance) with other items on the grid, including a stack that fills the first screen, and what it does not check on a narrow window; the first-run veil timing (AS-VC-05): the stored `y` comes from the boot window, the tiles appear after the modal; two tabs; the clamp to row 0 and the wrapped two-row block on narrow windows (decision 3); a zero-height first measurement.
- **Visual and layout:** does a block half a step above the middle of the rows read as "centered" when `F` is odd (an even number of rows: 40 px at 1280; 58 px above the window center at H 700); the top gap above the block at 1280×800 (336 px from the window edge) against the bottom gap (392 px); a two-row block at 500 and 320 px; a very tall window (row 12 at 2160 px) and a low one (row 0); no new vertical scroll when the block fits; the new link or restored metric in row 0 above the block.
- **Accessibility and copy:** the tab order and the focus ring of tiles that now sit mid-screen; the Add menu and tooltips of a tile in a middle row; no new strings; the status line stays a bottom overlay that is not part of the rows; the CHANGELOG and architecture wording.
- **Owner confirm (default in brackets):**
  1. The status line: is an overlay that may cover the block in windows under about 146 px acceptable, or must rows be reserved for it? (overlay, no reserved rows)
  2. A new link or a restored metric is drawn in row 0, above the block that sits in the middle: acceptable, or should `placeNew` also prefer the rows near the block? (`placeNew` unchanged, row 0)
  3. The rounding: with an odd number of free rows, `floor` puts the extra row below (the block half a step above the middle); `ceil` would put it above. (`floor`)
