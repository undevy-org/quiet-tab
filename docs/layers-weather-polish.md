## Terms

- **`RUN53_BASE`**: `848effd197ce183ec70493efc0be7548e7796f3b`, the head of `main` before this run. Every comparison "as before the run" below (rectangles, pixels, request counts, rebuild counts, heights) is made against a checkout of this commit, never against the live `origin/main`, which contains the change once the run is merged and would make the comparison empty.
- **The error slot**: `[data-dialog-error]` (`role="alert"`) of a `.desktop-dialog`. **The footer**: `.favorite-form__footer`, sticky while the dialog scrolls (`docs/layers-low-window.md` decision 13). **Scrolls**: `data-scrolls="true"` on the dialog.
- **The chip**: `#desktop-status`. **The chip reserve**: `--status-reserve` on `:root`, px, the distance from the window bottom to the chip's top while the chip exists (decision 12 of the layers spec).
- **Gone-link recovery**: `recoverFromGoneLink` (a write on a link or tile another tab deleted, or a cleared storage healed).
- **The locked list**: the wizard's starter list after Finish when the flag write was refused (`data-starters-locked="true"`, a keyboard scroll stop).
- **A shown weather tile**: in the displayed state at least one item with `type: "weather-metric"` and `enabled: true`. The city hint tile stands for an enabled metric, so it counts. A tab whose grid is unreadable or newer has no items and so no shown tile.
- **Fresh cache**: `0 <= now - fetchedAt < WEATHER_CACHE_TTL_MS` (30 minutes, `src/weatherShared.js`) for the same city (decision 4).
- **Due**: `weatherRefreshDue(result, now)` (`src/weatherUiState.js`): an `error`, a `stale`, or a `ready` result whose data is 30 minutes old or more. Unchanged.
- **The stale state**: a weather result with `status: "stale"` (saved data, the last fetch failed), also while an attempt retries.
- **A group**: a `.segmented` radiogroup (Icon, Color, Size in Add link and Edit link; Size in Edit weather). **An option**: a `.segmented__option`. **The bold-face reserve**: the room the label of an option keeps for its bold face while it is not selected (decision 12).
- **Beside layout**: a form row whose label stands left of its control (`.favorite-form__row` as a flex row). **Stacked layout**: under the stacking media query of `src/surfaces.css` (`max-width: 400px` or `max-width: 25rem`, where `rem` in a media query is the browser's default font size: the threshold is 400 px at 16 px, 500 px at 20 px, 525 px at 21 px and 600 px at 24 px) the label stands above the control. There is no stacking rule in `src/controls.css`. **The nowrap block**: `@media (max-width: 451px)` of `src/surfaces.css`, where an option has `padding: 0 5px` and `white-space: nowrap` and cannot wrap.

## Decisions

### Part A (row Р53): quiet defects of layers, weather and code

1. **A shown error follows a window resize (item 128).** The window `resize` handler (a zoom fires it too) calls `syncDialogScrolls` itself and, in the same animation frame, if the open `.desktop-dialog` shows its error slot (not hidden) and scrolls, and the slot's bottom plus its 5 px margin lies below the footer's top edge, scrolls the dialog instantly by the rule of decision 6 of `docs/layers-low-window.md`: the same function (`scrollDialogErrorIntoView`), the same two branches (field and slot together if they fit, else the slot wins). It does not wait for the size observer of `watchDialogScrolls`, so no painted frame shows the slot under the footer once the layout has settled. The target is the one `showDialogError` used when it showed this error (remembered when the error is shown, for example on the dialog; for an empty `field` argument that is the field `invalidFieldFor(message)` chose, or the submit button), not recomputed from the DOM. If the remembered target is hidden at the moment of the resize (its rectangle is zero, for example the Custom icon field after the Icon went back to "From site"), the submit button is the target of that resize. If the slot is already above the footer nothing moves. A change of the dialog's content (the Icon switch showing the Custom icon row, a font load) is not a trigger: it keeps the behaviour of `RUN53_BASE`. The focus, `aria-invalid`, `aria-describedby` and the text do not change. Only a `.desktop-dialog` with a shown slot is concerned: the first-run wizard, the city modal alone, the Reset grid screen and a running drag do not take part and move nothing. **Ruling (марафон, на проверку Киру): the trigger is the window resize only; альтернатива: every size change of the dialog or its form (the Icon switch would also pull the slot back); цена ошибки: after switching Icon to Custom in a scrolling dialog with a shown error the slot may stay under the footer until the next scroll (as on `RUN53_BASE`), with the alternative the dialog moves under a user who has just clicked a control.** **Ruling (марафон, на проверку Киру): when the city modal is stacked over Edit weather (the dialog is `inert` and covered), a resize still scrolls the dialog's error into view and never moves the focus out of the modal; альтернатива: do nothing while the modal is open; цена ошибки: the covered dialog's error is under its footer when the modal closes after a resize, with the alternative a scroll the user cannot see happens under the modal.**
2. **The chip reserve is current whenever the chip is shown (item 129).** `showDesktopStatus` is the one point. Right after it sets the text and clears `hidden` (a non-empty text), it reads `desktopStatus.getBoundingClientRect().height` (a forced layout; the border-box height the observer writes, which `offsetHeight` would round) and writes `--status-reserve` at once: the chip's border-box height plus `--status-chip-offset-bottom`, instead of waiting for the `ResizeObserver`. The observer stays and writes the same value later. The hide path is not changed: `showDesktopStatus("")` still runs `keepHoldAcrossChipRelease` first, which reads the reserve of the shown chip and hands it to `--drag-hold` in the same task, and nothing writes `0px` before it (the observer writes it afterwards, as on `RUN53_BASE`). Two callers reveal something right after showing the chip and so profit: (a) in both branches of `recoverFromGoneLink` (with a dialog and without; a healed storage included) the status text is shown before focus and reveal, so the neighbour (or Settings after a heal) ends at least 6 px inside the window and above the chip (decision 7 of the layers spec, unchanged); (b) in `runDesktopMutation`'s heal branch the chip is shown before the Add link handler calls `closeDesktopDialog()` and `revealAddedTile(added.id)`, which read `isSafelyInsideWindow` and the root `scroll-padding-bottom`, so the new tile ends above the chip. A chip shown while the dialog is still in the DOM is unpainted but keeps its reserve (decision 2 of the layers spec), so showing it first changes nothing the user sees. Every other caller behaves as before, except that its reserve appears one observer tick earlier with the same value.
3. **Ring room for the locked list (item 130).** `scroll-margin: 5px` on the locked list, a literal with the same reason as the city modal's rule (the widest ring is the forced-colors outline, 2 px + 2 px offset = 4 px, plus one pixel for integer scroll offsets). The ring itself stays: the solid `--focus-ring` outline, 2 px, offset 0, outside the list's box (decision 9 of the layers spec); the candidate "inset ring over the rows" of backlog row 130 is not taken because that spec chose a ring that rows cannot cover. Where the card's scrollport is lower than the ring (1280×300: 266 px against 280 px) the margin cannot make the ring whole, and the side that is cut depends on the direction the focus came from; that is Accepted exception 10.
4. **A cache from the future is not fresh (item 138).** `isCacheFresh` needs `0 <= now - fetchedAt < WEATHER_CACHE_TTL_MS`. A cache whose `fetchedAt` is later than `now` (the clock moved back) is fetched again at open like an old one; if that fetch fails the result is `stale` with that cache, as for any old cache. `weatherRefreshDue` already treats a future `fetchedAt` as not due and `formatUpdatedAge` reads a negative age as "Updated just now"; both stay.
5. **A refused reset does not redraw (item 167 b).** In `resetGrid`'s catch the busy flag of its own generation is released without a render: the unreadable screen is not rebuilt and its `p[role=alert]` is not inserted again. The rest of the catch stays: the dialog closes with the post-close guard, focus goes to the screen's Reset grid button, the chip says `Couldn't reset your grid. Try again in a moment.` (decision 6 of `docs/unreadable-grid-reset.md`, AS-UGR-12). The re-announcement of the alert when the dialog closes is outside this run (item 170, point 2).
6. **Code with no visible effect (items 161, 165, 167).** (a) `healReadDesk` releases the busy lock in a `finally`. (b) In `retryWeather` `downgrade` is a boolean (`Boolean(...)`). (c) `src/desktopLayout.js`: the sentence "The same value is max(0, floor((min(rows, CEILING_REFERENCE_ROWS) - blockRows) / 2))" and the "Callers: ..." line leave the comment of `centeredDefaultRow` (the formula stays once, in the code and the first sentences); the `viewportRows` comment says "`centeredDefaultRow` counts a window of more than CEILING_REFERENCE_ROWS rows as CEILING_REFERENCE_ROWS rows". (d) The load in `newtab.js` computes `const metaKind = inspectWidgetsMeta(rawMeta)` once and uses it for the `newer` and the `invalid` exits. (e) The comment of `resetUnreadableWidgets` in `src/widgetsStore.js` names the accepted window between the `get` and the `remove` by what it is, not by "Accepted exception 2". The source pins of `test/newtabSource.test.js` and `test/weatherSource.test.js` that match the old text move with it (the number of `it(` does not drop: the pre-push hook).

### Part B (row Р54): weather texts and requests, a steady segmented group

7. **A stale tile says "Last known" (item 140, Q2 A).** `readyModel` in `src/weatherTiles.js` knows whether the data is stale. For the temperature metric in the stale state, including the stale state while an attempt retries, the sentence `Currently <t>°.` becomes `Last known: <t>°.`; the rest of the sentence (`Today at 15:00`, `yesterday at 15:00`) and the order of the parts stay as on `RUN53_BASE`: a stale tile reads `STALE_PREFIX`, the age sentence (when there is one), `Last known: <t>°.`, the rest; a stale tile while an attempt retries reads `Trying again…` followed by the model's data sentence alone (`Last known: <t>°.`, the rest), with no `STALE_PREFIX` and no age sentence, as on `RUN53_BASE`. A ready tile keeps `Currently <t>°.`; an error tile is unchanged. The model's `description` feeds the hidden description and the tooltip, so both change together. The other three metrics have no such word, except UV (Accepted exception 2).
8. **No lone word at the end of a message (item 140).** `text-wrap: pretty` on the shared `.tooltip` (so every tooltip, not only the stale ones, may break differently), on the error slot of the city modal and the wizard (`.city-modal .status--full`), and on the page chip `.desktop-status`. The sentence "Try again in a moment" stays (Ruling 2 of row 136).
9. **No shown tile, no weather request (item 156, Q3 A).** A request to Open-Meteo for the stored city (the forecast and the air quality) is made only while the displayed state has a shown weather tile. That gates three entries: the load at open, which now starts from the tile-appears hook of decision 10 (the boot no longer calls `startWeather` on its own), the automatic attempt at a return and at `online` (`retryWeather({ automatic: true })`, so `weatherRefreshDue` is not even asked), and the manual attempt (a retry press needs a tile). Not gated, because they act from a tile or the wizard: choosing or changing the city (`setCity`, `selectLocation`). Reading the stored city and cache from storage is not a request and may stay. With no shown tile nothing is drawn, announced or written because of the weather: no status text, no cache write. A request already in flight when the last tile is hidden is not cancelled (a service call cannot be): it finishes, its result is kept and its cache write stays (Accepted exception 8).
10. **A tile that appears asks once, when due; the load at open goes the same way (item 156, Q3 A).** One hook, one place that every route of a changed state passes (the first render at open, restoring a metric through the Add menu, a grid re-read that applies another tab's change, a heal, `recoverFromGoneLink`, a refresh on return). It remembers whether the displayed state it last saw had a shown weather tile; the initial value is "none", so the first render of a tab that has a shown tile is itself the change "none to some" and the load at open is started by the hook, not by a separate call from the boot. The hook is run from a microtask after the render, never synchronously inside the render, and it updates its remembered value before it starts anything. When the state changes from no shown tile to at least one the weather is loaded once, and the branch is chosen by whether this tab's load at open has already started (a flag of the tab, set when the hook starts that load and never cleared), not by `effectiveWeatherResult()`. The first such change, before the load at open has started, starts the load at open: the `startWeather` path, not `retryWeather` (`weatherService.initialize()`: a cache younger than 30 minutes is served with no request, otherwise one forecast and one air-quality request). It does so also when `effectiveWeatherResult()` is already an `error` because the read of the city failed: on `RUN53_BASE` the boot's `startWeather` runs beside a failed city read and leaves the retry state alone, so the tiles stand retry-ready while the load hangs and a manual press supersedes it (`dg-88` AS-WRL-02 (b2)). Every later change, once the load at open has started, starts the automatic attempt of a return (`retryWeather({ automatic: true })`), which runs only when `weatherRefreshDue(effectiveWeatherResult())` says the shown result is due; a result that is not due (a young `ready`, `no-location`, none) is shown at once with no request. While a city change runs (`weatherChanging`, so `effectiveWeatherResult()` is `null`) the hook starts nothing: the change owns the tiles. Like a return, the automatic attempt of the hook does not start while `navigator.onLine === false`, and it does not start inside the 3 s pause after a failed attempt (nothing starts it when the pause ends: the next return, `online` or restore does); the load at open still starts offline, as the boot did on `RUN53_BASE`, because it serves the cache or shows the error. **One flag "a weather load is in flight" is shared by the open load, the hook and `retryWeather`:** while it is set neither the hook nor an automatic attempt (a return, `online`) starts another, so no path that needs no press runs two attempts at once (the 3 s pause of `weatherUiState` applies to the retry as before). For a failed read of the city this differs from `RUN53_BASE`, where an automatic attempt supersedes the open load: Accepted exception 12. **A manual Retry press is not stopped by the flag:** it supersedes an open load as on `RUN53_BASE` (`retryWeather` raises `weatherGeneration`, `dg-88` AS-WRL-02 (b2)); the flag then belongs to the pressed attempt, and the superseded load, when it ends, neither clears nor sets it. The flag is cleared when its attempt ends by an answer, an error, the 15 s timeout or a dropped late result; a successful city change (`changeCity`) supersedes an open attempt, clears the flag when its own answer is applied (as it resets the retry state today) and a late answer of the superseded attempt does not touch it. A tile hidden and restored while an attempt is in flight starts nothing new. What the tiles show until the answer: with no held result, the loading state; with a held `ready` result that is due, the held values (the attempt starts silently, as at a return); with a held `error` or `stale` result, the retrying state of the tile. **Ruling (марафон, на проверку Киру): a returning tile uses the held result when it is not due, and does not always re-read the cache; альтернатива: always call `initialize()` when a tile appears (a cache read, a flash of loading); цена ошибки: a tile shows data up to 30 minutes old that another tab has already refreshed, with the alternative the tile flashes its loading state on every restore.**

## Acceptance scenarios

Premises that depend on the machine (window sizes, counts of links, the clock) are printed by the scenario and asserted before the action, as in `dg-86`. Light and dark themes where a ring or a pixel is compared.

Methods used by several scenarios (the scenario states which it uses):
- **Base.** "Before the run" always means `RUN53_BASE` (Terms): the harness builds that commit from the git object (`buildFromRef`) and runs the same steps on it. A comparison with the live `origin/main` is never an assertion, because after the merge it compares the code with itself. The numbers of § Live measurement are the printed expectation for `RUN53_BASE`.
- **One step.** A sampler records the dialog's `scrollTop` in every animation frame from the `resize` call until two frames after the last one, and counts `scroll` events: "moved in one step" means at most one `scroll` event and a series of `scrollTop` values that changes at most once (from the old value to the final one).
- **Pixel-equal.** Screenshots of the dialog card's box, device scale factor 1, in the same Chromium and the same run for the candidate and for `RUN53_BASE`, animations and transitions off, text caret hidden (`caret-color: transparent`), the same focus and checked state, compared per colour channel with tolerance 0. Two measured exceptions, both bounded. (a) Render noise: each state is captured up to 6 times per build; a pixel counts as different only when the values it took in the candidate's captures and in `RUN53_BASE`'s share none, and up to 4 such pixels per state are allowed (identical builds disagree on 1 or 2). (b) Option-label glyphs: pixels within 2 px of the text-range rectangle of an option label are compared only by count (at most 60 differing pixels per state inside that mask), because the label's text is centred in a label as wide as the bold face needs, so its left edge is the sum of two 1/64 px halvings and differs from the single halving of `RUN53_BASE` by 1/64 px in about a quarter of the labels; for those labels the text-range rectangle (±0.5 px), the text, the weight, the colour, the font size and the radio state are compared as well.
